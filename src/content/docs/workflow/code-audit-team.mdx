Every pull request in a GAIA project is audited before it merges. The audit is not one reviewer but a team. Each member is responsible for a set of files, and a pull request is reviewed by every member whose files it changes. The audit runs locally in your Claude Code session. Nothing runs Claude on GitHub Actions.

A hook enforces it: `gh pr merge` is denied until every member whose files changed has approved the change. The `GAIA-Audit` required check stops anyone from skipping the audit by merging with the button on github.com.

## Members

The list of members (the roster) lives in `.gaia/audit-ci.yml` under `auditors:`. Each entry assigns a set of file patterns (globs) to a member. Two members ship:

| Member | Owns | Reviews for |
|---|---|---|
| `code-audit-frontend` (the default member) | The app and its tooling: `frontend/app/**`, `frontend/test/**`, `frontend/.storybook/**`, `frontend/.playwright/**`, the package manifests and lockfile, build and lint configs, `frontend/.claude/**`, `frontend/CLAUDE.md`, and root tooling such as `.npmrc` and `.nvmrc` | Security, performance, fit with the existing architecture, edge cases, accessibility, and maintainability: problems that take understanding what the code is meant to do and how data moves through it, beyond what lint and types catch. Library-specific rules for shadcn/ui, `cn`, Conform, the form components, React patterns, and react-i18next load from `frontend/.claude/agents/code-audit-frontend/`. |
| `code-audit-github-workflows` | `.github/workflows/*.yml` and `.github/actions/**/*.yml` | Workflow YAML problems: unsafe third-party actions, script injection, too-broad permissions, and mishandled secrets. |

Each file goes to the first member whose pattern matches it, and the default member's patterns are checked last, so a workflow file belongs to `code-audit-github-workflows`. A file no member is responsible for belongs under `unowned:` in the same file. The audit itself does not check this. After you change the roster, run `bash .gaia/scripts/verify-audit-roster.sh` by hand: it fails when a file has no member and is not listed under `unowned:`, or when a pattern matches no file at all.

Members only report problems. They never edit a file. A separate fixer makes the repairs, and a script checks each repair before it is kept.

### Editing the roster

`.gaia/audit-ci.yml` ships with GAIA, and you edit its values to adjust the audit: add patterns for code you add beside `frontend/`, list paths that need no review under `unowned:`, or set the light-review keys below. If the file has no `auditors:` block, the audit refuses to run rather than falling back to a built-in list.

## Per-member clearance

Each member's approval (its clearance) covers exactly what the branch changed in that member's files, plus GAIA's own audit scripts. You will notice three effects:

- **Members run in parallel**, in any order.
- **A commit outside a member's files never sends it back to review.** A CHANGELOG line or a wiki page triggers no new review.
- **Merging the base branch into yours does not trigger a new review**, unless the merge commit contains its own edit, or a change from the base branch lands within three lines of your branch's changes.

A member sent back to review looks only at what changed since its last approval or refusal, plus any of its findings still open.

### Light review

A small change since a member's last full review can go to a cheaper Sonnet reviewer, if the member turns this on with `light_review: true` in `.gaia/audit-ci.yml`. `light_line_cap` sets the largest change that qualifies (at most 50 lines), and `light_hard_full` lists patterns that always get a full review. `code-audit-frontend` has light review on by default, but its configs, package manifests, test folders, and Claude setup files always get a full review. Whenever GAIA cannot confirm a change qualifies for light review, the full member runs.

## Severity

Every finding is graded on one scale:

| Severity | Effect on approval |
|---|---|
| **Critical** | Must be fixed. |
| **Major** | Must be fixed, or acknowledged with a stated reason. |
| **Minor** | Never blocks approval. Fixed by default. |

A fourth grade, `severity:investigate`, marks a tech-debt issue whose severity cannot be judged yet. See [`/gaia-debt`](/maintenance/debt/#labels).

Every finding, Minor included, gets an outcome. By default it is fixed. Otherwise it is accepted as a known trade-off (a residual), waived, or filed as an issue, each with a reason. Findings about architecture come to you to decide.

**Out-of-scope findings** (problems the audit notices outside the pull request's own change) are filed as `tech-debt` issues through the [`file-tech-debt`](/maintenance/debt/#how-issues-are-filed) skill. A non-security finding in a file the pull request already changes can instead be recorded as waived in the pull request body, but only when it passes two checks (for example, that this change did not introduce it). **Security findings are never filed publicly.** They become issues only when the repository is private. Otherwise they stay in a local record, with secrets removed, under `.gaia/local/audit/security/`, and you are told only how many there were and where the records are.

## The audit loop

An `audit-loop-unit` sub-agent runs the audit rounds a few at a time, outside your main session. In each round, the members review, a fixer repairs what they found, a script checks the repairs, and the Quality Gate runs before the round's fixes are committed. Your session holds only a short report per unit, so a long audit does not fill your context.

The loop needs **Claude Code 2.1.292 or later**. Run `claude update` if a unit stops and names the version.

### The branch checkpoint

Each round's fixes need reviewing in the next round, so left alone the loop would never stop. A hook limits it on each branch. It checks in with you when:

- your session's context reaches its checkpoint line,
- rounds stop making progress (the number of findings caused by the branch stops going down, or each repair causes new findings on the lines it wrote), or
- the maximum number of rounds is reached.

At a checkpoint Claude shows you where things stand (rounds run, findings per round, its assessment, what remains by severity, and the cost so far) and asks one question with fixed answers:

- **Continue audit in this session** or **Continue audit in a new session**: allow one more batch of rounds. The new-session option prints a continuation prompt in a code block. Run `/clear`, then paste it.
- **Accept the remainder**: offered only when the loop has a reason to stop (for example, round 10 is reached, rounds stop making progress, or only Minor findings remain from round 6 on), no remaining finding is Critical or security-related, and every member left readable findings for the round. Runs one last review round with no fixes, and records what remains under `## Accepted residuals (recorded, not fixed)` in the pull request body.
- **Stop and file the remainder**: files the remaining findings as tech-debt issues and leaves the pull request open.

Only a person can answer. If the question is not available, type one of these as the whole prompt:

```text
audit-grant <n>
```

```text
audit-accept
```

You can also type `audit-accept` on purpose to accept when the menu does not offer it. Claude never types, writes, or fakes either line, and a hook blocks Claude from writing to the checkpoint's saved state. A session running with nobody watching never asks and never grants more rounds: it pushes the round's fixes, leaves the pull request open, and prints the `audit-grant` line for you to type later.

**Why:** a loop nobody watches keeps spending with no limit. And without the checkpoint, "is another round worth it?" would be decided mid-loop by the session least able to judge it. See the [gate reference](/reference/gates/#audit-checkpoint).

## Posting GAIA-Audit

Claude posts the `GAIA-Audit` success status last: once every member involved has approved the current change, every finding from every round is fixed or recorded, and the last push has landed. Posting it any earlier would mark the pull request done while findings were still being decided. Posting success also marks the draft pull request ready for review.

A refusal posts a `GAIA-Audit` failure straight away. That cancels any earlier success for the same commit, so GitHub's auto-merge cannot merge the pull request anyway.

Pull requests the audit does not need to review (no changed file is assigned to any member, or a `chore(deps)` update from `/update-deps` that only changes package manifests) get the check posted by the merge hook itself, as `skipped: out of scope` or `skipped: chore(deps) manifest-only`.

<Aside type="note">
A pull request merged from the GitHub UI without going through Claude (a raw Dependabot pull request, for example) never gets the check posted, so it waits on `GAIA-Audit` forever. Ask Claude to merge it once: the hook works out which case it is, posts the check, and allows the merge.
</Aside>

## What lands in the pull request

- **`## Audit rounds`**: total rounds, rounds per member, light reviews, and human grants.
- **`## Accepted residuals (recorded, not fixed)`**: accepted findings, each with a unique key so the same one is not recorded twice. [`/gaia-residue`](/maintenance/residue/) reads these later.
- **A findings comment**, posted on every `gh pr merge`, carrying every round's findings from every member. Security and Critical findings are left out of it and appear only as a count.

Each `gh pr merge` also prints the pull request's [cost](/reference/cost/).

## Reading a refusal

The merge hook denies `gh pr merge` with one reason and one next step. The common ones:

| You see | What it means | Next step |
|---|---|---|
| A member has no clearance for the current change | That member has not reviewed the latest commit to its files, or refused it | Let Claude run the audit loop. A refusal goes away only when the finding is fixed (which changes the reviewed files) or a Major is acknowledged with a reason. |
| The base tip is not a commit in this checkout | The audit measures your change against the base branch GitHub reports, and your checkout has not fetched it | `git fetch origin` |
| GitHub cannot be reached | The audit cannot read the pull request's base branch | Fix the `gh` failure it prints, and check `gh auth status` |
| More than one merge base with the base tip | Git's history allows more than one answer to what your branch changed | `git merge --no-edit refs/remotes/origin/<base>` |
| A cross-repository (fork) pull request | A local audit would run the fork's own audit scripts with your credentials | Review the fork's changes to GAIA's Claude setup files by hand, push the branch to your own repository, and audit that pull request |

After changing a pull request's base branch on GitHub, reset the recorded base with `git config --unset branch.<branch>.gaia-audit-base`.

Claude waits for a queued merge with `bash .gaia/scripts/pr-wait-merge.sh --pr <N>`, which stops as soon as the pull request has a conflict or a required check fails.

Every gate the audit can raise has a row in the [gate reference](/reference/gates/).
