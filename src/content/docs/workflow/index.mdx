This page shows how GAIA's pieces fit together in normal use, so you know what to do once setup is done.

## Mostly, you just prompt Claude

Working in GAIA is the same as working in Claude Code: describe what you want in plain language. GAIA loads its rules, skills, and guardrails when the session starts, so an ordinary request already runs through them. You do not invoke them.

Ask for a component, a fix, a refactor:

```
> Add a date-range filter to the saved-search panel.
```

The code skills (TypeScript, React, Tailwind, tests) and the scaffolders trigger on their own from how you phrase the request. Most sessions never touch a slash command.

Notice the prompt did not ask for a test. GAIA works test-first: for a feature or a bug fix, Claude writes a failing test, then the code that makes it pass. A commit hook backs this up, refusing to commit a new test that was never seen to fail first.

## Every committed change follows one lifecycle

When Claude commits work, with or without a command, it follows the same steps:

1. **Claims** the GitHub issue the work closes with an `in-progress` label, so nobody else starts it.
2. **Names** the branch from one library, `<type>/[<issue>-]<slug>` for ad-hoc work.
3. **Isolates** the work in a git worktree by default, so parallel tasks never touch each other.
4. **Commits** through the Quality Gate and the commit hooks, with a Conventional Commits message, and opens a **draft** pull request.
5. **Audits** it with the [Code Audit Team](/workflow/code-audit-team/).
6. **Merges** only when you ask.
7. **Cleans up** back to a pulled default branch.

Before each commit, the Quality Gate runs typecheck, lint, tests, Playwright, a dev-server smoke test, and the build, and the hooks block risky actions in the background. See [Work lifecycle](/workflow/work-lifecycle/) for the details, and [Git hooks and conventions](/workflow/git-conventions/) for the commit and title rules.

## When to reach for a command

The `/gaia-*` commands are for specific moments, not everyday driving:

| When you're... | Reach for | Why |
| --- | --- | --- |
| Starting a feature whose shape isn't settled | [`/gaia-spec`](/workflow/spec/) | Pins down intent and acceptance tests, saves a SPEC, and plans it in the same session. |
| Turning a big feature into parallel work | [`/gaia-plan`](/workflow/plan/) | Breaks it into phased workstreams with shared contracts and a ready-to-run kickoff prompt. |
| A GAIA command or hook misbehaved | [`/gaia-forensics`](/workflow/forensics/) | Diagnoses the misfire and, if it is a bug, drafts a filing-ready report. |

**When to skip them.** Small, clear changes do not need a spec or a plan. "Fix the timezone bug in the invoice header" is just a prompt. Spec and plan earn their overhead on larger, fuzzier work.

## Resuming work

Long work resumes from one small state file, `STATE.md`, in its run folder under `.gaia/local/runs/<branch>/`. When a session's context runs heavy, Claude saves its place and asks whether to continue here or clear and resume; on clear, it prints a continuation prompt in a fenced code block to paste after `/clear`. You can ask Claude for a continuation prompt at any time. See [Work lifecycle](/workflow/work-lifecycle/#resuming-long-work).

The 1.x `/gaia-handoff` and `/gaia-pickup` commands are gone.

## A feature, start to finish

1. **Settle what to build.** Run `/gaia-spec add saved-search filters`. It asks a few questions, confirms the intent and the acceptance tests in plain English, and saves a SPEC. Then it plans the SPEC in the same session and ends with a kickoff prompt.
2. **Build it.** Run `/clear` and paste the kickoff prompt. The orchestrator works in its own worktree, renders the SPEC's browser-flow acceptance tests as failing Playwright specs, builds each phase with sub-agents, commits each phase after the Quality Gate, and opens a draft pull request.
3. **Audit and merge.** The [Code Audit Team](/workflow/code-audit-team/) reviews the pull request, a fixer repairs what it finds, and Claude posts `GAIA-Audit` once it clears. Ask Claude to merge.
4. **Handle the small stuff directly.** "Fix the date formatting in the invoice header" is a single prompt. Claude still claims the issue, isolates the change, and audits the pull request.

You will not run every step for every task. Reach for as much of the loop as the work needs, and prompt directly for the rest.

[What you meet, and when](/getting-started/what-you-meet/) walks through when each of these first fires.

## Maintenance commands

<Aside type="tip">
You rarely reach for these yourself, and you do not have to memorize them. They surface on the statusline when they are due.
</Aside>

| When... | Reach for | Why |
| --- | --- | --- |
| The Claude integration feels off | [`/gaia-fitness`](/maintenance/fitness/) | Lints skills, rules, commands, agents, hooks, and settings, grades them, and heals your own files. |
| Memory or auto-loaded files have drifted | [`/gaia-cleanse`](/maintenance/cleanse/) | Finds duplication, contradictions, and stale guidance against the wiki. |
| Tech-debt issues have piled up | [`/gaia-debt`](/maintenance/debt/) | Fixes the backlog, highest severity first, through the audit gate. |
| The audit keeps flagging the same thing | [`/gaia-codify`](/maintenance/codify/) | Turns the recurring finding into a check, a skill, or a rule. |
| Accepted residuals have piled up | [`/gaia-residue`](/maintenance/residue/) | Dismisses, keeps, or promotes each trade-off recorded at merge. |
| Serena is missing a language | [`/gaia-serena-sync`](/maintenance/serena-sync/) | Adds it to Serena's index on your yes. |
| The wiki has fallen behind the code | [`/gaia-wiki`](/maintenance/wiki/) | Syncs, consolidates, and lints the project wiki Claude reads from. |
| Dependencies are stale or vulnerable | [`/update-deps`](/maintenance/update-deps/) | Resolves security advisories, then updates packages by group. |
| A new GAIA release is out | [`/update-gaia`](/maintenance/update-gaia/) | Merges the release into your project without clobbering your changes. |
