`/gaia-plan` breaks a complex feature into phases of parallel workstreams with frozen interface contracts. It does not implement anything. It writes a plan folder and hands you one prompt to paste into a fresh session, where an orchestrator executes the plan.

## When to use it

Reach for `/gaia-plan` when the work spans several files or modules, has slices that can run in parallel (UI, service layer, tests), or benefits from giving each slice its own fresh sub-agent context.

For one-line fixes or single-file edits, skip the ceremony and prompt Claude directly.

For a feature whose intent is not settled yet, run [`/gaia-spec`](/workflow/spec/) instead. It plans its SPEC in the same session, so you do not run `/gaia-plan` separately.

## How to invoke

```
/gaia-plan a feature description in plain English
```

From a saved SPEC:

```
/gaia-plan SPEC-005
```

Non-interactive:

```
/gaia-plan auto a feature description
```

`auto` asks no questions: the planner runs on Opus, and decomposition-audit findings are applied or recorded in the plan's README. A description is required.

With no description at all, `/gaia-plan` asks for one.

## What gets produced

| Plan | Folder |
|---|---|
| From a SPEC | `.notebook/specs/SPEC-NNN/plan/` (a second plan for the same SPEC is `plan-2/`) |
| With no SPEC | `.notebook/plans/PLAN-NNN/`, numbered from the notebook catalog |

Inside it:

| File | Purpose |
| --- | --- |
| `README.md` | The task graph: phase order, which tasks run in parallel in each phase and on which model, the frozen interface contracts shared across tasks, and the source SPEC. |
| `ORCHESTRATOR.md` | The runbook the orchestrator follows: isolation, phase order with quality gates, sub-agent prompt templates, the pre-merge audit, the git flow, and stop conditions. |
| `KICKOFF.md` | The prompt a fresh session reads to start orchestrating. |
| `task-<name>.md` | One per workstream, self-contained for a fresh sub-agent: contracts, files to touch, acceptance criteria, dependencies. |
| `PROGRESS.md` | Written during execution: one entry per completed or halted phase. |

## The flow

1. **Pre-flight.** The same housekeeping `/gaia-spec` runs, plus the offer to pull when your GAIA version lags.
2. **Resolve the SPEC**, if one was named. A SPEC reference that resolves to nothing stops with an error rather than silently planning without it.
3. **Pick the planner model.** On Opus or Fable the planner inherits your model. Otherwise Claude asks: Opus (recommended), Fable, or your current model. The planner runs at your session's effort, so a higher `/effort` drafts a deeper plan.
4. **Plan.** A planner sub-agent writes the folder. A planner that runs heavy on context hands off to a fresh one.
5. **Verify.** A deterministic check confirms every required file and step, and that every UAT the SPEC defines is routed to a task.
6. **Decomposition audit.** On any non-trivial plan (parallel tasks, several phases, or a shared contract), parallel lenses audit the task graph and the contracts, plus SPEC coverage for a SPEC's plan, before a cold orchestrator builds against them. A trivial plan skips it.
7. **Report.** A cost line (or, for a SPEC's plan, a box covering the spec and the plan), then the prompt:

   ```text
   Read /absolute/path/to/plan/KICKOFF.md and execute it.
   ```

   Type `/clear` and paste it.

## Execution

The orchestrator runs in the fresh session:

- **Isolation** follows your team's [isolation policy](/workflow/work-lifecycle/#3-isolate), worktrees by default. The branch is named `<type>/spec-<nnn>-<slug>` for a SPEC's plan or `<type>/plan-<nnn>-<slug>` otherwise, where `<type>` is the Conventional Commits type of the change. The PR Conventions check expects the pull request title's type to match.
- **Each phase** dispatches its tasks to sub-agents, Sonnet by default. Sub-agents only edit files: they never commit, push, or run git that rewrites the shared working tree. The orchestrator commits each phase after the Quality Gate passes.
- **A task that runs heavy** on context hands off to a fresh agent. When one task yields too often, the plan halts for you.
- **The pull request** opens as a draft and goes through the [Code Audit Team](/workflow/code-audit-team/) before it merges.

### Resuming a plan

Running the kickoff again on a plan that already completed phases shows each verified phase with its commit and asks:

- **Resume** at the first incomplete phase
- **Restart from Phase 1**
- **Abandon**: stop without re-running, committing, merging, or deleting anything

A plan generated before a GAIA update keeps the steps it was generated with until you regenerate it.

### UAT specs

For a plan from a SPEC, each browser-flow UAT is rendered into a Playwright spec under `frontend/.playwright/e2e/` **before Phase 1**, committed on its own and marked as expected to fail (`test.fail()`). Each one must pass before the phase that owns it can commit. Executors are told not to rewrite a rendered spec's assertions to make it pass, since the spec is the SPEC's contract.

Before the audit, the orchestrator checks that every rendered spec still asserts its contract (an `uat-fidelity-judge` agent reads each one). When the implementation and a UAT logically diverge, the plan halts so the SPEC can be reopened, instead of quietly changing what was agreed.

The SPEC is closed around the merge of its implementation.

<Aside type="note">
A 1.x plan branch named `plan/spec-<nnn>-...` or `spec-<nnn>-...` is legacy. GAIA no longer creates those names. See [Upgrading from 1.x](/getting-started/upgrading/#every-other-machine) to rename an unmerged one.
</Aside>
