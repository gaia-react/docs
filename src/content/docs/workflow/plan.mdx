`/gaia-plan` splits a complex feature into phases. Each phase holds tasks that can run at the same time, and the types and interfaces the tasks share (the contracts) are fixed up front so the tasks fit together. It does not write the code. It writes a plan folder and gives you one prompt to paste into a fresh session, where an orchestrator (the session that runs the plan) carries it out.

## When to use it

Reach for `/gaia-plan` when the work spans several files or modules, has parts that can be built at the same time (UI, service layer, tests), or would benefit from giving each part its own sub-agent with a fresh context.

For one-line fixes or single-file edits, skip the plan and prompt Claude directly.

For a feature whose goal is not settled yet, run [`/gaia-spec`](/workflow/spec/) instead. It plans its SPEC in the same session, so you do not run `/gaia-plan` separately.

## How to invoke

```
/gaia-plan a feature description in plain language
```

From a saved SPEC:

```
/gaia-plan SPEC-005
```

Non-interactive:

```
/gaia-plan auto a feature description
```

`auto` asks no questions: the planner runs on Opus, and problems the plan audit finds are fixed or written down in the plan's README. A description is required.

With no description at all, `/gaia-plan` asks for one.

## What gets produced

| Plan | Folder |
|---|---|
| From a SPEC | `.notebook/specs/SPEC-NNN/plan/` (a second plan for the same SPEC is `plan-2/`) |
| With no SPEC | `.notebook/plans/PLAN-NNN/`, numbered from the notebook catalog |

Inside it:

| File | Purpose |
| --- | --- |
| `README.md` | The overview: phase order, which tasks run at the same time in each phase and on which model, the fixed contracts the tasks share, and the source SPEC. |
| `ORCHESTRATOR.md` | The step-by-step instructions the orchestrator follows: where the work runs, phase order with quality gates, prompts for each sub-agent, the audit before merge, the git steps, and when to stop. |
| `KICKOFF.md` | The prompt a fresh session reads to start orchestrating. |
| `task-<name>.md` | One per task, with everything a fresh sub-agent needs: contracts, files to change, acceptance criteria, dependencies. |
| `PROGRESS.md` | Written during execution: one entry per completed or halted phase. |

## The flow

1. **Before it starts.** The same housekeeping `/gaia-spec` runs, plus the offer to pull when your GAIA version is behind the remote.
2. **Find the SPEC**, if you named one. If no SPEC matches, it stops with an error instead of quietly planning without it.
3. **Pick the planner model.** On Opus or Fable the planner inherits your model. Otherwise Claude asks: Opus (recommended), Fable, or your current model. The planner runs at your session's effort, so a higher `/effort` drafts a deeper plan.
4. **Plan.** A planner sub-agent writes the folder. If the planner's context reaches the [red band](/workflow/work-lifecycle/#resuming-long-work), it hands off to a fresh one.
5. **Verify.** A script checks that every required file and step is there, and that every UAT (acceptance test) in the SPEC is assigned to a task.
6. **Plan audit.** On any plan with parallel tasks, several phases, or a shared contract, reviewers check how the work is split and the contracts, and for a SPEC's plan, that the plan covers the whole SPEC. This happens before an orchestrator with no memory of the planning builds from it. A simple plan skips this step.
7. **Report.** A cost line (or, for a SPEC's plan, a box covering the spec and the plan), then the prompt:

   ```text
   Read /absolute/path/to/plan/KICKOFF.md and execute it.
   ```

   Type `/clear` and paste it.

## Execution

The orchestrator runs in the fresh session:

- **Where it runs** follows your team's [isolation policy](/workflow/work-lifecycle/#3-isolate): a separate worktree by default. The branch is named `<type>/spec-<nnn>-<slug>` for a SPEC's plan or `<type>/plan-<nnn>-<slug>` otherwise, where `<type>` is the Conventional Commits type of the change. The PR Conventions check expects the pull request title's type to match.
- **Each phase** hands its tasks to sub-agents, Sonnet by default. Sub-agents only edit files: they never commit, push, or run git commands that change the shared checkout. The orchestrator commits each phase after the Quality Gate passes.
- **A task whose context reaches the red band** hands off to a fresh agent. When one task has to hand off too often, the plan stops and asks you.
- **The pull request** opens as a draft and goes through the [Code Audit Team](/workflow/code-audit-team/) before it merges.

### Resuming a plan

Running the kickoff again on a plan that already completed phases shows each verified phase with its commit and asks:

- **Resume** at the first incomplete phase
- **Restart from Phase 1**
- **Abandon**: stop without re-running, committing, merging, or deleting anything

A plan generated before a GAIA update keeps the steps it was generated with until you regenerate it.

### UAT specs

For a plan from a SPEC, each UAT routed to an end-to-end test is turned into a [Playwright](https://playwright.dev/) test under `frontend/.playwright/e2e/` **before Phase 1**. It is committed on its own and marked as expected to fail (`test.fail()`). The phase responsible for a test cannot commit until that test passes. Sub-agents are told not to change a test's assertions to make it pass, because the test is what the SPEC promised.

Before the audit, the orchestrator checks that every one of these tests still tests what the SPEC says (an `uat-fidelity-judge` agent reads each one). When the code and a UAT no longer agree, the plan stops so the SPEC can be reopened, instead of quietly changing what was agreed.

The SPEC is closed out after its implementation merges.
