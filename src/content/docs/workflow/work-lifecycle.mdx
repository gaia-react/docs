Every change Claude commits follows one lifecycle, whether a command drives it (`/gaia-plan`, `/gaia-debt`, a maintenance command) or you just asked for a fix in plain language:

1. **Claim** the issue, if the work closes one.
2. **Name** the branch.
3. **Isolate** the work in a worktree or a feature branch, per your team's policy.
4. **Commit** through the Quality Gate and open a **draft** pull request.
5. **Audit** the pull request with the [Code Audit Team](/workflow/code-audit-team/).
6. **Merge**, only when you ask.
7. **Clean up** back to a pulled default branch.

Every committed task gets a draft pull request, even when you did not ask for one. If you say you will review or commit an edit yourself, Claude leaves it uncommitted on your current branch and none of these steps apply.

## 1. Claim

When the work closes a GitHub issue, Claude reads the issue's labels first. An issue already labeled `in-progress` belongs to someone else, so Claude tells you and picks different work instead of competing for it. Otherwise it claims the issue:

```bash
gh issue edit <n> --add-label in-progress
```

The claim is released automatically when the pull request that closes the issue (with `Closes #<n>` in its body) merges through `gh pr merge` in a Claude session. Any other ending leaves the claim set, so remove it by hand with `gh issue edit <n> --remove-label in-progress`.

**Why:** when two agents or two people start the same issue, the work gets done twice and the two versions then conflict at merge. See the [gate reference](/reference/gates/#issue-claim).

A `tech-debt` issue is never claimed by hand: run `/gaia-debt <n>` instead, which owns that claim. See [`/gaia-debt`](/maintenance/debt/).

## 2. Name

Claude never makes up a branch name. One shared script (`branch-name-lib.sh`) generates every branch name GAIA creates, in the form `<kind>/<rest>`:

| Work | Branch |
|---|---|
| Ad-hoc work | `<type>/[<issue>-]<slug>`, for example `fix/142-login-redirect` |
| A plan from a SPEC | `<type>/spec-<nnn>-<slug>` |
| A plan with no SPEC | `<type>/plan-<nnn>-<slug>` |
| A tech-debt fix (`/gaia-debt`) | `debt/<n>-<slug>`, or `debt/<a>-<b>-batch` for a batch |
| Maintenance commands | `deps/`, `update/`, `wiki/`, `cleanse/`, `codify/`, `fitness/`, or `residue/` plus a timestamp |

`<type>` is the Conventional Commits type of the change (`feat`, `fix`, `chore`, and the rest). The pull request title uses the same type, and the advisory PR Conventions check compares them. See [Git hooks and conventions](/workflow/git-conventions/).

## 3. Isolate

Your team's isolation policy lives in `.gaia/project.json` as `isolation_policy`:

| Policy | What happens |
|---|---|
| `always-worktree` (default) | Every task runs in its own git worktree (a separate working copy of the repository), so tasks can run at the same time without touching each other or your checkout. Claude does not ask. |
| `prefer-worktree` | Claude suggests a worktree and you can choose a branch instead. |
| `prefer-branch` | Claude suggests a feature branch in your current checkout and you can choose a worktree instead. A second task started while you are on a feature branch still gets a worktree. |

A repo admin changes the policy with `/setup-gaia --reconfigure`. Saying "in a worktree" or "on a branch" in your request answers the question up front. Under `always-worktree`, though, a request for a branch still gets a worktree, and Claude tells you so.

<Aside type="note">
Uncommitted edits already in your checkout come along. On a feature branch they stay where they are. A worktree starts clean from the default branch, so Claude copies the edits into it as a patch and leaves your original copies untouched.
</Aside>

### Worktrees provision themselves

GAIA uses Claude Code's built-in worktrees under `.claude/worktrees/`. When a session enters one, GAIA renames its branch to the generated name and sets the worktree up:

- **Shared state is linked, not copied.** GAIA's machine-local state (`.gaia/local`), the [notebook](#where-specs-plans-and-research-live), and the main checkout's `frontend/.env` are linked into the worktree, so nothing written there disappears when the worktree is removed, and secrets are never copied.
- **Dependencies and typed routes install in the background.**
- **Each checkout has its own ports.** The main checkout keeps 5173 (dev) and 6006 (Storybook). Each worktree gets its own fixed set of ports for dev, Storybook, and Playwright. A server refuses to start on a port that is already taken instead of quietly picking another one. Read a tree's ports with `bash .gaia/scripts/ports.sh`.
- **A guard keeps edits in the right copy.** An edit to a file in a different checkout from the session's worktree is denied. Without this, an old absolute path from before the switch would silently change the wrong copy. See the [gate reference](/reference/gates/#worktree-path-mismatch).

If a worktree's links break, repair them with `bash .gaia/scripts/link-worktree.sh`. A worktree with no port file refuses `pnpm dev`, `pnpm storybook`, and `pnpm pw`. Fix it with `bash .claude/hooks/provision-worktree.sh <worktree path>`.

At every session start, GAIA lists merged worktrees that no live session is using, with the commands to remove them.

## 4. Commit and open the draft pull request

Every commit passes the commit hooks. A commit that touches source or build configuration also passes the Quality Gate: a simplify pass, a check for untranslated user-facing text, typecheck, lint, tests, Playwright, a quick dev-server check, and the build. A commit of only Markdown, `.claude/` files, or wiki pages skips the gate. The dev-server check runs `bash .gaia/scripts/dev-smoke.sh`, which starts this checkout's own dev server, checks that a page loads, and stops only the server it started. That way it never kills a server another session is using. The branch is pushed and the pull request opens as a draft with a Conventional Commits title. When the work closes an issue, `Closes #<n>` goes in the pull request body, never in a commit message. A squash merge copies commit messages into the final commit, and GitHub would close the issue from there no matter what the body says.

**Why draft:** reviewers should be notified when a pull request is ready, and in a GAIA project that is when the audit passes and posts its `GAIA-Audit` check. A pull request opened as ready notifies reviewers before any audit has run. When the audit passes, it marks the pull request ready. See the [gate reference](/reference/gates/#draft-pull-requests).

## 5. Audit

Claude runs the full audit on every pull request before merge, including small one-off changes. There is no shortcut. See [Code Audit Team](/workflow/code-audit-team/).

When you did not ask Claude to merge, it stops here and reports the pull request as ready to merge, leaving the branch, worktree, and pull request in place.

## 6. Merge

Claude squash-merges when you ask, then waits for the merge to land:

```bash
bash .gaia/scripts/pr-wait-merge.sh --pr <N>
```

The script ends with one result (`MERGED`, `CONFLICTING`, `CHECK_FAILED`, `TIMEOUT`, `CLOSED`). It stops as soon as the pull request has a conflict or a required check fails, instead of waiting forever. Cleanup runs only after `MERGED`. A hook blocks Claude from writing its own wait loop for the same reason: a loop that waits only for `MERGED` never ends once the merge can no longer happen.

## 7. Clean up

After `MERGED`, Claude removes the worktree (or switches off the feature branch), deletes the local branch, fetches, and pulls the default branch. It runs `pnpm install --frozen-lockfile` only when the pull changed `pnpm-lock.yaml`.

Cleanup never forces a pull and never stashes. Before removing a worktree it checks for uncommitted files and unpushed commits. If it finds either, it keeps the worktree and the branch, and tells you what is left and how to remove them. When the main checkout is on a branch another session holds, Claude skips the pull and says so.

## Where specs, plans, and research live

Specs, plans, and research live in one gitignored `.notebook/` folder at the main checkout:

- `.notebook/specs/SPEC-NNN/` (a SPEC's plan nests inside it)
- `.notebook/plans/PLAN-NNN/` for plans with no SPEC
- `.notebook/research/<date>-<topic>/`

Every worktree links to the main checkout's copy, so nothing written there is lost when a worktree is removed. Abandoned SPEC folders are kept for `GAIA_SPEC_RETENTION_DAYS` days (default 30), then deleted. Merged ones are deleted after the same period only once their layers are consolidated and their cost is in the usage ledger. Closed research that nothing refers to is deleted only after you confirm.

## Resuming long work

Work that spans sessions resumes from a small saved state, rewritten in place. Where it goes depends on the work:

- a `/gaia-plan` run saves to its own progress files, at a committed phase boundary
- `/gaia-spec` saves to its draft cache
- a research folder saves to its own state file
- other work on a branch saves to `.gaia/local/runs/<branch>/STATE.md`
- work on the default branch saves to `.gaia/local/runs/session-<session id>/STATE.md`

A resumed session reads that saved state and the run's artifact list and nothing else.

Claude cannot see how full its own context is, so the statusline tracks it in four bands. GAIA asks you to clear long before Claude Code's own automatic compaction, which only starts when the context window is nearly full:

| Band | On a 1M-token window | On a 200K-token window | What happens |
|---|---|---|---|
| Yellow | 250K tokens (25%) | 60K tokens (30%) | The statusline turns yellow. No question. |
| Red | 300K tokens (30%) | 100K tokens (50%) | Claude saves its place and asks. |
| Fire | 375K tokens | 125K tokens | Claude asks again and recommends clearing. |
| Skull | 450K tokens | 150K tokens | Claude asks again and recommends clearing. |

The red band sits at 300,000 tokens or half the window, whichever is smaller. Fire is 1.25 times red and skull is 1.5 times red. To ask even earlier, a person can lower the red band in `.gaia/local/protected/checkpoint-override.json`, for example `{"version":1,"context_checkpoint":{"ask_tokens":100000}}`. The file can only lower it, never raise it, and Claude cannot edit it.

**Why so early:** models get less reliable as their context grows long, long before the window is full. They recall and use information less accurately, especially information in the middle of a long context. Researchers call this context rot. See Chroma's [Context Rot](https://www.trychroma.com/research/context-rot) study, [Lost in the Middle](https://arxiv.org/abs/2307.03172) (Liu et al.), and Anthropic's [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). A long session also costs more: every turn sends the whole conversation again, so each step in a full session is billed for everything before it, even at the [cached rate](https://platform.claude.com/docs/en/build-with-claude/prompt-caching). A fresh session that resumes from a short saved state is both sharper and cheaper. GAIA's band values are tuned estimates, not measured limits.

When the context reaches the red band, Claude finishes the current step, saves its place, and asks one question:

- **Continue here**: keep working until the next band.
- **Clear and resume**: Claude prints a continuation prompt in a fenced code block. Run `/clear` and paste it.

At the fire and skull bands, the two fullest, Claude always recommends clearing. Sessions running with nobody watching never ask: they save and continue, and at the last band they save, print the continuation prompt, and stop.

You can also ask Claude for a continuation prompt at any time. It always arrives in a fenced code block, ready to paste.

## Commands that run only in the main checkout

`/setup-gaia`, `/gaia-debt`, and the maintenance commands (`/gaia-wiki`, `/gaia-residue`, `/gaia-codify`, `/gaia-fitness`, `/gaia-cleanse`, `/gaia-serena-sync`, `/update-deps`, `/update-gaia`) refuse inside a linked worktree and name the main checkout to run them from. The ones that change the repository create their own worktree or branch for the work. See the [Maintenance overview](/maintenance/#how-maintenance-commands-run).

Commands that start new work (SPECs, plans, tech-debt fixes, one-off changes) offer to pull first when your checkout's GAIA version is behind the remote. Resuming earlier work is never interrupted by that offer.
