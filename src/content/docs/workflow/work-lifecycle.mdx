Every change Claude commits follows one lifecycle, whether a command drives it (`/gaia-plan`, `/gaia-debt`, a maintenance command) or you just asked for a fix in plain language:

1. **Claim** the GitHub issue with an `in-progress` label, so nobody else starts it. This step runs only when the work closes an existing issue.
2. **Name** the branch with GAIA's shared naming script.
3. **Isolate** the work in its own git worktree (a second working copy of the repository) or a feature branch, per your team's policy, so tasks running at the same time never touch each other.
4. **Commit** through the Quality Gate and the commit hooks, with a Conventional Commits message, and open a **draft** pull request.
5. **Audit** the pull request with the [Code Audit Team](/workflow/code-audit-team/).
6. **Merge.** Ad-hoc work waits until you ask. Some commands merge their own pull request as part of the run.
7. **Clean up** back to a pulled default branch.

Every committed task gets a draft pull request, even when you did not ask for one. If you say you will review or commit an edit yourself, Claude leaves it uncommitted on your current branch and none of these steps apply.

## 1. Claim

Claiming applies only when the work closes an existing GitHub issue. Work with no issue behind it, such as a quick fix you asked for in a prompt, skips this step.

When there is an issue, Claude reads its labels first. An issue already labeled `in-progress` belongs to someone else, so Claude tells you and picks different work instead of competing for it. Otherwise it claims the issue:

```bash
gh issue edit <n> --add-label in-progress
```

The claim is released automatically when the pull request that closes the issue (with `Closes #<n>` in its body) merges through `gh pr merge` in a Claude session. Any other ending leaves the claim set, so remove it by hand with `gh issue edit <n> --remove-label in-progress`.

**Why:** when two agents or two people start the same issue, the work gets done twice and the two versions then conflict at merge. See the [gate reference](/reference/gates/#issue-claim).

A `tech-debt` issue is never claimed by hand: run `/gaia-debt <n>` instead, which owns that claim. See [`/gaia-debt`](/maintenance/debt/).

## 2. Name

Claude never makes up a branch name. One shared script (`branch-name-lib.sh`) generates every branch name GAIA creates, in the form `<kind>/<rest>`:

| Work | Branch |
|---|---|
| Ad-hoc work | `<type>/[<issue>-]<slug>`, for example `fix/142-login-redirect` |
| A plan from a SPEC | `<type>/spec-<nnn>-<slug>` |
| A plan with no SPEC | `<type>/plan-<nnn>-<slug>` |
| A tech-debt fix (`/gaia-debt`) | `debt/<n>-<slug>`, or `debt/<a>-<b>-batch` for a batch |
| Maintenance commands | `deps/`, `update/`, `wiki/`, `cleanse/`, `codify/`, `fitness/`, or `residue/` plus a timestamp |

**Why:** GAIA reads branch names back as well as writing them. The prefix tells it which workflow made a branch and which issue or SPEC it belongs to, so a resumed plan or `/gaia-debt` can find its own work. One script for both writing and reading means the two can never disagree.

`<type>` is the Conventional Commits type of the change (`feat`, `fix`, `chore`, and the rest). The pull request title uses the same type, and the advisory PR Conventions check compares them. See [Git hooks and conventions](/workflow/git-conventions/).

## 3. Isolate

Your team's isolation policy lives in `.gaia/project.json` as `isolation_policy`:

| Policy | What happens |
|---|---|
| `always-worktree` (default) | Every task runs in its own git worktree (a separate working copy of the repository), so tasks can run at the same time without touching each other or your checkout. Claude does not ask. |
| `prefer-worktree` | Claude suggests a worktree and you can choose a branch instead. |
| `prefer-branch` | Claude suggests a feature branch in your current checkout and you can choose a worktree instead. |

A repo admin changes the policy with `/setup-gaia --reconfigure`. Saying "in a worktree" or "on a branch" in your request answers the question up front. Under `always-worktree`, though, a request for a branch still gets a worktree, and Claude tells you so.

<Aside type="caution" title="Off the default branch, every policy uses a worktree">
The choice is only offered when your checkout is on `main` or `master`. If it is on any other branch, new work always gets its own worktree, under every policy, and Claude does not ask. The branch you are on already holds work, and a second task's changes must not get mixed into it.
</Aside>

<Aside type="note">
Uncommitted edits already in your checkout come along. On a feature branch they stay where they are. A worktree starts clean from the default branch, so Claude copies the edits into it as a patch and leaves your original copies untouched.
</Aside>

### Worktrees provision themselves

GAIA uses Claude Code's built-in worktrees under `.claude/worktrees/`. When a session enters one, GAIA renames its branch to the generated name and sets the worktree up:

- **Shared state is linked, not copied.** GAIA's machine-local state (`.gaia/local`), [The Notebook](/workflow/notebook/), and the main checkout's `frontend/.env` are linked into the worktree. Nothing written there disappears when the worktree is removed, and your secrets stay in one file instead of being duplicated into every worktree. Separately, Claude cannot read `.env` files in any checkout. See the [gate reference](/reference/gates/#reading-secrets).
- **Dependencies install and typed routes are generated in the background.** A new worktree has no `node_modules`, so GAIA runs `pnpm install --frozen-lockfile` in it. It then runs React Router's `typegen`, which writes [TypeScript](https://www.typescriptlang.org/) types for each route's URL params and loader data, so route code type-checks against the worktree's own routes. See React Router's [type safety guide](https://reactrouter.com/explanation/type-safety). Both steps run as a background job so the session does not wait for them, and Claude is told where the job's log is while it runs.
- **Each checkout has its own ports.** See [Ports per worktree](#ports-per-worktree).
- **A guard keeps edits in the right copy.** An edit to a file in a different checkout from the session's worktree is denied. When a session moves into a worktree, Claude may still hold absolute paths it used in the main checkout. Those paths still point to real files, just in the wrong copy, so an edit through one would change the main checkout without any warning. See the [gate reference](/reference/gates/#worktree-path-mismatch).

If a worktree's links break, repair them with `bash .gaia/scripts/link-worktree.sh`.

### Ports per worktree

Every checkout gets its own dev, [Storybook](https://storybook.js.org/), and [Playwright](https://playwright.dev/) ports, so you can run the app in several worktrees at the same time without one server taking another's port.

- **The main checkout keeps the default ports:** 5173 (dev) and 6006 (Storybook).
- **Each worktree gets a numbered slot**, the lowest one free, and its ports are the defaults plus that number. Slot 1 is 5174 and 6007, slot 2 is 5175 and 6008. A worktree keeps its slot every time a session returns to it. Slots cover the `frontend/` package only.
- **`pnpm dev`, `pnpm storybook`, and `pnpm pw` use the worktree's ports automatically.** They read them from `frontend/.gaia-ports`, which GAIA rewrites each time a session enters the worktree, so don't edit it. To see a tree's ports, run `bash .gaia/scripts/ports.sh` (`--field dev`, `storybook`, `site-url`, or `slot` prints one value).
- **A taken port is refused, never swapped.** A server refuses to start on a port that is already in use instead of quietly picking another one. Playwright reuses a running server only when it belongs to its own worktree. A direct `storybook dev` skips this check and can move to another port, so start Storybook with `pnpm storybook`.
- **A worktree with no port file refuses `pnpm dev`, `pnpm storybook`, and `pnpm pw`** rather than borrow the main checkout's ports. Fix it with `bash .claude/hooks/provision-worktree.sh <worktree path>`.
- **Leftover servers are stopped for you, carefully.** At a later session start, GAIA stops servers that a Claude session started once that session has ended, and servers left running by a removed worktree. A server you started yourself is never stopped automatically, and Claude asks before stopping anything on a port another worktree owns.

## 4. Commit and open the draft pull request

Every commit passes the commit hooks. A commit that touches source or build configuration also passes the [Quality Gate](/workflow/code-audit-team/#quality-gate), the full set of checks on the `frontend/` package. The branch is pushed and the pull request opens as a draft with a Conventional Commits title. When the work closes an issue, `Closes #<n>` goes in the pull request body, never in a commit message. A squash merge copies commit messages into the final commit, and GitHub would close the issue from there no matter what the body says.

**Why draft:** reviewers should be notified when a pull request is ready, and in a GAIA project that is when the audit passes and posts its `GAIA-Audit` check. A pull request opened as ready notifies reviewers before any audit has run. When the audit passes, it marks the pull request ready. See the [gate reference](/reference/gates/#draft-pull-requests).

## 5. Audit

Claude runs the full audit on every pull request before merge, including small one-off changes. There is no shortcut. See [Code Audit Team](/workflow/code-audit-team/).

For ad-hoc work you did not ask Claude to merge, it stops here and reports the pull request as ready to merge, leaving the branch, worktree, and pull request in place.

## 6. Merge

Who decides when to merge depends on what started the work:

| Work | When it merges |
|---|---|
| Ad-hoc work (a plain request) | Only when you ask. A later message asking to merge counts. |
| A plan run from its kickoff prompt | At the end of the run, Claude prints a summary and asks one question: merge it, or hold the merge. |
| [`/gaia-debt`](/maintenance/debt/), [`/gaia-wiki`](/maintenance/wiki/), [`/update-deps`](/maintenance/update-deps/), [`/gaia-cleanse`](/maintenance/cleanse/) | As part of the run, once the audit passes (`/gaia-wiki` posts its own) and the required checks are green. You do not need to ask. |
| [`/gaia-residue`](/maintenance/residue/), [`/gaia-codify`](/maintenance/codify/), [`/gaia-fitness`](/maintenance/fitness/) | The command asks before it merges, and you can leave the pull request open instead. |
| [`/update-gaia`](/maintenance/update-gaia/) | It opens a draft pull request and stops. You merge it when you are ready. |

Claude squash-merges, then waits for the merge to land:

```bash
bash .gaia/scripts/pr-wait-merge.sh --pr <N>
```

The script ends with one result (`MERGED`, `CONFLICTING`, `CHECK_FAILED`, `TIMEOUT`, `CLOSED`). It stops as soon as the pull request has a conflict or a required check fails, instead of waiting forever. Cleanup runs only after `MERGED`. A hook blocks Claude from writing its own wait loop for the same reason: a loop that waits only for `MERGED` never ends once the merge can no longer happen.

## 7. Clean up

After `MERGED`, Claude removes the worktree (or switches off the feature branch), deletes the local branch, fetches, and pulls the default branch. It runs `pnpm install --frozen-lockfile` only when the pull changed `pnpm-lock.yaml`.

Cleanup never forces a pull and never stashes. Before removing a worktree it checks for uncommitted files and unpushed commits. If it finds either, it keeps the worktree and the branch, and tells you what is left and how to remove them. When the main checkout is on a branch another session holds, Claude skips the pull and says so.

A worktree that cleanup kept, or one whose remote branch was deleted without the worktree being removed, is listed at every session start, with the commands to remove it. The list shows only worktrees whose work is merged and that no live Claude session is using. GAIA never removes them itself: Claude removes a listed worktree only when you name it.

## Resuming long work

Work that spans sessions resumes from a small saved state, rewritten in place. Where it goes depends on the work:

- A `/gaia-plan` run saves to its own progress files, at a committed phase boundary
- `/gaia-spec` saves to its draft cache
- A research folder saves to its own state file
- Other work on a branch saves to `.gaia/local/runs/<branch>/STATE.md`
- Work on the default branch saves to `.gaia/local/runs/session-<session id>/STATE.md`

A resumed session reads that saved state and the run's artifact list and nothing else. A saved place does not last forever. Once its branch no longer exists, GAIA deletes a branch's run folder after 7 days. A save made on the default branch is deleted after 30 days.

### Context bands

Claude cannot see how full its own context is, so the [statusline](/workflow/statusline/#the-context-bar) tracks it in four bands. GAIA asks you to clear long before Claude Code's own automatic compaction, which only starts when the context window is nearly full:

| Band | On a 1M-token window | On a 200K-token window | What happens |
|---|---|---|---|
| Yellow | 250K tokens (25%) | 60K tokens (30%) | The statusline turns yellow. |
| Red | 300K tokens (30%) | 100K tokens (50%) | The statusline turns red. Claude saves its place and asks. |
| 🔥 | 375K tokens (37.5%) | 125K tokens (62.5%) | The statusline shows 🔥. Claude asks again and recommends clearing. |
| 💀 | 450K tokens (45%) | 150K tokens (75%) | The statusline shows 💀. Claude asks again and recommends clearing. |

The red band sits at 300,000 tokens or half the window, whichever is smaller. 🔥 is 1.25 times red and 💀 is 1.5 times red. To ask even earlier, a person can lower the red band in `.gaia/local/protected/checkpoint-override.json`, for example `{"version":1,"context_checkpoint":{"ask_tokens":100000}}`. The file can only lower it, never raise it, and **Claude cannot edit it**.

When the context reaches the red band, Claude finishes the current step, saves its place, and asks one question:

- **Continue here**: keep working until the next band.
- **Clear and resume**: Claude prints a continuation prompt in a fenced code block. Run `/clear` and paste it.

At 🔥 and 💀, the two fullest bands, Claude always recommends clearing. Sessions running with nobody watching never ask: they save and continue, and at 💀 they save, print the continuation prompt, and stop.

You can also ask Claude for a continuation prompt at any time. It always arrives in a fenced code block, ready to paste.

### Why so early?

Models get less reliable as their context grows long, long before the window is full. They recall and use information less accurately, especially information in the middle of a long context. Researchers call this context rot. Chroma's [Context Rot](https://www.trychroma.com/research/context-rot) study tested 18 models and found that performance drops as input grows, even on simple tasks. See also [Lost in the Middle](https://arxiv.org/abs/2307.03172) (Liu et al.) and Anthropic's [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

A long session also costs more. Claude Code sends the whole conversation with every request, so each step in a full session is billed for everything before it, even at the [cached rate](https://code.claude.com/docs/en/costs#why-usage-climbs-in-a-long-session). A fresh session that resumes from a short saved state is both sharper and cheaper. GAIA's band values are tuned estimates, not measured limits.

### Why not wait for auto-compaction?

Claude Code compacts a session on its own when the context fills: it replaces the conversation with a summary and carries on. By default that happens at the model's context limit, or at about 967K tokens on a 1M-token window. See [Default auto-compact thresholds](https://code.claude.com/docs/en/model-config#default-auto-compact-thresholds). Clearing at the red band beats waiting for it in three ways:

- **The summary is written late.** By the time compaction runs, the session is far past the point where context rot sets in. The model writes the summary from that long context, so it can miss or blur details that mattered.
- **What carries over is chosen.** At the red band, Claude saves a short state of at most 4 KB: the goal, open decisions, what is done, and the one next step. A compaction summary is the model's condensed version of the whole conversation.
- **It costs less.** Every turn before compaction is billed for the full history, and compaction itself is a [request over that whole history](https://code.claude.com/docs/en/prompt-caching#compacting-the-conversation). Claude Code's own docs note that when you want a fresh start, `/clear` costs nothing.

## Commands that run only in the main checkout

`/setup-gaia`, `/gaia-debt`, and the maintenance commands (`/gaia-wiki`, `/gaia-residue`, `/gaia-codify`, `/gaia-fitness`, `/gaia-cleanse`, `/gaia-serena-sync`, `/update-deps`, `/update-gaia`) refuse inside a linked worktree and name the main checkout to run them from. The ones that change the repository create their own worktree or branch for the work. See the [Maintenance overview](/maintenance/#how-maintenance-commands-run).

Commands that start new work (SPECs, plans, tech-debt fixes, one-off changes) offer to pull first when your checkout's GAIA version is behind the remote. Resuming earlier work is never interrupted by that offer.
