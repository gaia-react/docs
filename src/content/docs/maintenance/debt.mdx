`/gaia-debt` fixes the `tech-debt` backlog: the GitHub issues the [Code Audit Team](/workflow/code-audit-team/), [`/gaia-residue`](/maintenance/residue/), and [`/gaia-cleanse`](/maintenance/cleanse/) file for problems they found outside the change they were reviewing. Each run resolves **one fix unit**, a single issue or a batch of related issues, on its own branch, carries it through the same audit gate every feature pull request passes, and merges it. The pull request carries one `Closes #N` per issue, so the merge closes them.

## When to use it

When open `tech-debt` issues exist, the statusline shows:

```
🐛 /gaia-debt (N issues)
```

`N` is the open count, not counting issues someone has already claimed.

## How to invoke

```
/gaia-debt
```

No argument: Claude orders the backlog and offers the top of it as a menu. When the top issue belongs to a cluster of related issues (same file, same directory and finding class), the batch is offered too.

```
/gaia-debt 142
```

One issue number fixes that issue. If it heads a cluster, Claude offers to take the cluster with it.

```
/gaia-debt 142 157 161
```

Several numbers name your own batch, fixed together on one branch and one pull request. The batch is scored against a size budget; an over-budget batch offers smaller subsets or lets you force it.

Add `worktree` or `branch` (optionally after `use`) at the end to pick the isolation mode, for example `/gaia-debt 142 use branch`. Your team's [isolation policy](/workflow/work-lifecycle/#3-isolate) can still override it.

Anything else stops with the accepted form. A named number that cannot be drained (closed, not `tech-debt`, claimed, or parked) stops with its reason. The 1.x `fix`, `list`, and `why` subcommands are gone.

## How the backlog is ordered

A plain sort, with no model call:

1. **Severity**, highest first: `severity:critical`, then `severity:major`, then `severity:minor`. An issue with no severity label sorts with minor.
2. **Age**, oldest first.

Issues labelled `in-progress`, `debt:spec-pending`, or `debt:spec-active`, and issues graded `severity:investigate`, are set aside and never offered. When everything left is `investigate`, Claude says so and names each open question instead of reporting an empty backlog.

Each offer also notes when an issue's cited file no longer exists (`[stale: path gone]`).

## What one run does

1. **Claims** every issue in the unit with the `in-progress` label, straight after you pick, so a teammate's session never starts the same issue. A claim leaked by a session that died mid-fix is released on the next run.
2. **Re-checks each issue against your code** before cutting a branch: every cited `file:line` must still hold what the issue says, every count the fix depends on must still hold, and each issue's comments are read (a newer comment that corrects the body governs). A mismatch releases the claim and stops, because which of the issue and the code is wrong is your call. In a batch, a failing issue is dropped and the rest continue.
3. **Screens for security.** On a public or internal repository, a security-sensitive issue is never fixed in a public pull request. It is set aside, its claim released, and you are told only how many.
4. **Screens for size.** An issue whose fix needs a design SPEC is handed to [`/gaia-spec`](/workflow/spec/) instead: Claude prints the handoff and parks the issue under `debt:spec-pending` (handed off) or `debt:spec-active` (a SPEC is underway).
5. **Isolates** the fix on a `debt/<n>-<slug>` branch (or `debt/<a>-<b>-batch`), in a worktree by default.
6. **Fixes** every issue in the unit, runs the Quality Gate once, commits, and opens a draft pull request with one `Closes #N` per issue. The commit type is the type of the change (`fix`, `refactor`, `test`); the 1.x `debt` type is refused.
7. **Audits and merges** with no second confirmation, then checks that the merge closed exactly the intended issues, and cleans up.

A stop at the audit's branch checkpoint, a merge still queued, or a failing check keeps the claim, since the work is still in flight. A pull request closed without merging releases it.

The run ends with a [cost line](/reference/cost/).

**Why claim tech-debt issues only through `/gaia-debt`:** it owns the claim and the stale-claim release. A claim set by hand on a `tech-debt` issue is released on the next run as stale.

## Labels

Every tech-debt issue carries a severity, and filed issues carry footprint and difficulty grades:

| Label | Meaning |
|---|---|
| `severity:critical` | Wrong, or will produce broken work. Drained first. |
| `severity:major` | A significant gap or defect. Drained before minor findings. |
| `severity:minor` | Real but small. Fixed by default, never ignorable. |
| `severity:investigate` | Severity cannot be judged yet. The issue must name the open question and what would settle it. At most three may be open at once, and they are never drained until re-graded. |
| `footprint:narrow` | One logical unit in one file, no contract change. |
| `footprint:wide` | Spans files, changes a contract, or is structural. |
| `footprint:spec` | Must start with a design SPEC. Drains through `/gaia-spec`. |
| `difficulty:easy` | The fix is determined by the issue and the cited code. |
| `difficulty:medium` | The fix has a design decision the surrounding code settles. |
| `difficulty:hard` | The fix has a design decision the surrounding code does not settle. |
| `in-progress` | Someone is working the issue right now. |
| `debt:spec-pending`, `debt:spec-active` | Parked on a SPEC handoff, or a SPEC underway. |

The grades are advisory: Claude can upgrade or downgrade a footprint after reading the code. To return an `investigate` issue to the backlog, answer its question and re-grade it in one edit: `gh issue edit <n> --remove-label severity:investigate --add-label severity:<tier> --body-file <path>`, with the answer in the body. See [Labels](/reference/labels/) for the full registry.

## How issues are filed

The `file-tech-debt` skill is the one way a finding becomes a `tech-debt` issue, used by the audit loop, `/gaia-residue`, `/gaia-cleanse`, and by you ("file this as tech-debt"). It:

- builds a dedup key (`<!-- gaia-debt-key: v1 class=... path=... line=... -->`) and skips a finding that already has an open issue, or one declined (closed as not planned, or labelled `wontfix`);
- checks the labels and key offline before creating the issue, refusing a malformed filing instead of leaving it for a drain to trip over;
- files **security findings only when the repository reads as private**, checked twice. Otherwise it writes a redacted local record under `.gaia/local/audit/security/` and reports a count and that path, nothing more.

<Aside type="note">
`/gaia-debt` fixes issues; it does not file them. Use `file-tech-debt`, or let the audit file them, to add to the backlog.
</Aside>
