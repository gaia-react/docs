`/gaia-debt` fixes the `tech-debt` backlog: the GitHub issues the [Code Audit Team](/workflow/code-audit-team/), [`/gaia-residue`](/maintenance/residue/), and [`/gaia-cleanse`](/maintenance/cleanse/) file for problems they found outside the change they were reviewing. Each run fixes **one unit** of work: a single issue, or a batch of related issues. It works on its own branch, passes the same audit every feature pull request passes, and merges. The pull request carries one `Closes #N` per issue, so the merge closes them.

## When to use it

When open `tech-debt` issues exist, the statusline shows:

```
🐛 /gaia-debt (N issues)
```

`N` is the number of open issues, not counting issues someone is already working on.

## How to invoke

```
/gaia-debt
```

No argument: Claude orders the backlog and offers the top of it as a menu. When the top issue belongs to a group of related issues (the same file, or the same directory and kind of finding), the whole group is offered too.

```
/gaia-debt 142
```

One issue number fixes that issue. If it leads a group of related issues, Claude offers to fix the group with it.

```
/gaia-debt 142 157 161
```

Several numbers make your own batch, fixed together on one branch and one pull request. The batch is checked against a size limit. If it is too big, Claude offers smaller subsets or lets you go ahead anyway.

Add `worktree` or `branch` (optionally after `use`) at the end to choose where the fix happens, for example `/gaia-debt 142 use branch`. Your team's [isolation policy](/workflow/work-lifecycle/#3-isolate) can still override it.

Any other argument stops and shows the accepted form. An issue number that can't be fixed this way (closed, not labelled `tech-debt`, already claimed, or parked) stops with the reason.

## How the backlog is ordered

A plain sort, with no AI judgment involved:

1. **Severity**, highest first: `severity:critical`, then `severity:major`, then `severity:minor`. An issue with no severity label sorts with minor.
2. **Age**, oldest first.

Issues labelled `in-progress`, `debt:spec-pending`, or `debt:spec-active`, and issues graded `severity:investigate`, are set aside and never offered. When only `investigate` issues are left, Claude says so and lists each one's open question instead of reporting an empty backlog.

Each offer also notes when an issue's cited file no longer exists (`[stale: path gone]`).

## What one run does

1. **Claims** every issue in the unit with the `in-progress` label as soon as you pick, so a teammate's session never starts the same issue. If a session dies mid-fix and leaves a claim behind, the next run releases it.
2. **Re-checks each issue against your code** before creating a branch. Every `file:line` the issue cites must still contain what the issue says, and every count the fix depends on must still be right. Claude also reads each issue's comments; a newer comment that corrects the description wins. If anything doesn't match, Claude releases the claim and stops, because only you can decide whether the issue or the code is wrong. In a batch, a failing issue is dropped and the rest continue.
3. **Checks for security issues.** On a public or internal repository, a security-sensitive issue is never fixed in a public pull request. It is set aside and its claim released, and you are told only how many there were.
4. **Checks the size.** An issue big enough to need a design SPEC goes to [`/gaia-spec`](/workflow/spec/) instead. Claude prints what to run next and parks the issue under `debt:spec-pending` (handed off) or `debt:spec-active` (a SPEC is underway).
5. **Creates a branch** for the fix, `debt/<n>-<slug>` (or `debt/<a>-<b>-batch`), in a worktree by default.
6. **Fixes** every issue in the unit, runs the Quality Gate once, commits, and opens a draft pull request with one `Closes #N` per issue. The commit type is the type of the change (`fix`, `refactor`, `test`), never `debt`.
7. **Audits and merges** without asking you again, then checks that the merge closed exactly the intended issues, and cleans up.

The claim stays in place when the audit stops at its branch checkpoint, when a merge is still queued, or when a check fails, since the work is not finished. Closing the pull request without merging releases it.

The run ends with a [cost line](/reference/cost/).

**Why claim tech-debt issues only through `/gaia-debt`:** it manages the claim, including releasing claims left behind. A claim you set by hand on a `tech-debt` issue looks abandoned, so the next run releases it.

## Labels

Every tech-debt issue carries a severity. Filed issues also carry a footprint (how much code the fix touches) and a difficulty:

| Label | Meaning |
|---|---|
| `severity:critical` | Wrong, or will produce broken work. Drained first. |
| `severity:major` | A significant gap or defect. Drained before minor findings. |
| `severity:minor` | Real but small. Fixed by default, never ignorable. |
| `severity:investigate` | Severity cannot be judged yet. The issue must name the open question and what would settle it. At most three may be open at once, and they are never drained until re-graded. |
| `footprint:narrow` | One self-contained change in one file, with no change to a contract (how other code uses it). |
| `footprint:wide` | Spans files, changes a contract, or changes the code's structure. |
| `footprint:spec` | Must start with a design SPEC. Drains through `/gaia-spec`. |
| `difficulty:easy` | The issue and the cited code already make the fix clear. |
| `difficulty:medium` | The fix needs a design decision, and the surrounding code shows the answer. |
| `difficulty:hard` | The fix needs a design decision the surrounding code does not answer. |
| `in-progress` | Someone is working the issue right now. |
| `debt:spec-pending`, `debt:spec-active` | Parked on a SPEC handoff, or a SPEC underway. |

The grades are guidance only: Claude can change a footprint after reading the code. To return an `investigate` issue to the backlog, answer its question and re-grade it in one edit: `gh issue edit <n> --remove-label severity:investigate --add-label severity:<tier> --body-file <path>`, with the answer in the body. See [Labels](/reference/labels/) for the full registry.

## How issues are filed

The `file-tech-debt` skill is the one way a finding becomes a `tech-debt` issue, used by the audit loop, `/gaia-residue`, `/gaia-cleanse`, and by you ("file this as tech-debt"). It:

- adds a key to each issue (`<!-- gaia-debt-key: v1 class=... path=... line=... -->`) so the same finding is never filed twice, and skips a finding that already has an open issue or was declined (closed as not planned, or labelled `wontfix`);
- checks the labels and key before creating the issue, and refuses a badly formed one instead of leaving it for `/gaia-debt` to trip over later;
- files **security findings only when the repository is private**, checked twice. Otherwise it writes a redacted local record under `.gaia/local/audit/security/` and reports a count and that path, nothing more.

<Aside type="note">
`/gaia-debt` fixes issues; it does not file them. Use `file-tech-debt`, or let the audit file them, to add to the backlog.
</Aside>
