`/gaia-codify` looks at what the [Code Audit Team](/workflow/code-audit-team/) keeps finding across merged pull requests and proposes a guard so the problem stops coming back. For each repeat problem it recommends the lightest fix that would work (the one that adds least to what Claude reads on every task), explains it in plain language, and asks you once to accept the plan. Nothing is authored or switched on without your answer.

It runs like every [maintenance command](/maintenance/#how-maintenance-commands-run): from the main checkout, on a branch of its own, ending in a pull request. Only you start it, by typing it; Claude never runs it on its own.

## When to use it

The statusline nudges you with `🔨 /gaia-codify (<reason>)`:

- Before your first completed review, it counts recurring patterns: `/gaia-codify (3 recurring patterns)`.
- After a completed review, it stays quiet until something changes, then names it: a new recurring pattern, a pattern that has grown noticeably, or a change in how findings are counted.

On every `gh pr merge`, a hook posts the pull request's findings in a machine-readable form. Those posts are what the count reads.

## What counts as recurring

A kind of finding (its finding class) becomes a candidate once it appears on **3 or more different merged pull requests within the last 90 days**, at any severity, and no rule from an earlier run already covers it. Findings the audit could not place in a class are counted too, and surface as their own signal when they recur.

The count reads your merged pull requests through `gh`. When it cannot, the run says so ("this is not an all-clear") instead of reporting nothing.

## How it judges the form

For each candidate, it first checks whether an existing rule, skill, hook, or Quality Gate step already covers the territory, and recommends editing that before creating anything new. Then it picks the lightest form that fits:

| Pattern | Recommended form | What `/gaia-codify` does |
|---|---|---|
| An existing tool already catches it | Make that check stop the change instead of only warning, or add it to the Quality Gate | Edits the existing setup |
| It can be caught by a lint rule, hook, or test | An automated check | Writes a sketch of the hook and script for you to finish. Nothing is switched on. |
| The lesson is a procedure ("do these steps in this order") | A skill | Writes a `SKILL.md` outline for you to finish. Nothing is switched on. |
| A judgment call no tool can catch | A written rule that loads only for matching paths | Writes the rule file under `.claude/rules/`, scoped by `paths:` to where the finding recurs |

A written rule is the weakest option: it advises instead of enforcing, and Claude has to read it on every matching task. So before recommending one, it asks what quick evidence would show the rule actually changes behavior. If it can't name any, it recommends defer or decline instead.

## The flow

1. **Explain each candidate in plain language**: what keeps going wrong, one concrete example (the file and what was wrong there), how often as a share ("on 106 of the last 394 audited pull requests, about 1 in 4"), what the recommendation would actually do, and why.
2. **Show the whole plan** as one table.
3. **Ask once**:
   - **Accept all recommendations** (recommended)
   - **Change some**: pick rows, then choose **approve**, **decline**, **defer**, or **redirect** (a different form) for each
   - **Stop without changes**: nothing is authored or recorded
4. **Apply** your choice for each candidate. Approved rule edits land in the working tree on the run's own branch.
5. **Publish** approved changes as one pull request at the end, merged only on your answer.

### Decline and defer

- **Decline** records, on this machine only, that you are not acting on the pattern. It comes back once the pattern has grown by at least 3 more pull requests and its share of audited pull requests has risen by at least a quarter (5/4 of the share when you declined). While either count covers fewer than 20 audited pull requests, the raw counts are compared instead of shares. The record lives in `.gaia/local/codify/` and is never shared, so a teammate still sees the nudge.
- **Defer** records nothing of its own. The candidate still appears in the next review; the nudge stays quiet until the pattern grows or the counting changes.

## Promoted rules

A rule `/gaia-codify` writes carries a one-line comment after its frontmatter saying where it came from:

```markdown
<!-- gaia-harden: promoted from recurring finding_class <class>; pruned by /gaia-cleanse on obsolescence/redundancy/supersession/duplication only, never for non-recurrence -->
```

That comment is what stops the pattern from being counted again. [`/gaia-cleanse`](/maintenance/cleanse/) treats a marked rule like any other, except it never removes one because its pattern stopped showing up: a pattern that stops showing up means the rule is working.

The run ends with a [cost line](/reference/cost/).
