`/gaia-release` cuts a new release of GAIA itself. It is invoked by **Steven only**. The command and the `gaia-maintainer` binary it drives are excluded from the release bundle by `.gaia/release-exclude`, so no project scaffolded from GAIA has them.

## Why contributors should know it exists

Contributors who change CLI source, hooks, rules, or shipped wiki content land in trees a release will eventually package. The release validates those trees in three ways:

- **Manifest regeneration.** `.gaia/manifest.json` assigns each file in the bundle a class (`owned`, `shared`, or `wiki-owned`). [`/update-gaia`](/maintenance/update-gaia/) reads it to decide which files to overwrite, three-way merge, or leave alone. A newly shipping file needs an explicit ship-or-withhold decision before the manifest is regenerated.
- **Bundle-time scrub.** The release workflow stages a tree from `git ls-files`, subtracts `.gaia/release-exclude`, then strips `gaia:maintainer-only` blocks and runs leak checks. Any leak fails the build.
- **Distribution test gate.** The release workflow runs the distribution harness against the staged tree before anything publishes.

If a change touches surface the release validates, expect the next release to surface any drift.

## What /gaia-release does

The command runs on a clean default branch with a `patch`, `minor`, or `major` argument. At a behavioral level it:

- bumps the version in `.gaia/VERSION`, `package.json`, and `frontend/package.json`;
- graduates the CHANGELOG's `## [Unreleased]` section into a dated `## [X.Y.Z]` entry;
- resets `wiki/log.md` to release-clean content, so projects scaffold from a clean slate;
- regenerates `.gaia/manifest.json` and rebuilds the bundled CLIs;
- commits on a `release/vX.Y.Z` branch and opens a pull request, which passes the same checks and the same [Code Audit Team](/workflow/code-audit-team/) audit as any other;
- tags the merge commit once it lands, which triggers [release.yml](/contributors/ci/#releaseyml);
- then brings `create-gaia`, the website, and these docs into lockstep with the release.

A 2.x release ships `gaia-bundle-<tag>.tar.gz` with a `.sha256` asset, and any migration notes it needs travel inside the bundle under `.gaia/migrations/` (see [Migration notes](/maintenance/update-gaia/#migration-notes)). While 1.x projects can still reach a 2.x release, the release body opens with the routing line that sends a 1.6.1 project to the 2.0.0 migration.

## The two CLI binaries

The CLI bundles two binaries from two entry points. `.gaia/cli/gaia` is the binary every project gets; `.gaia/cli/gaia-maintainer` carries the release surface and is excluded by `.gaia/release-exclude`. esbuild keeps the release code out of the shipped binary, so `gaia` has no way to cut a release. See [CLI surface](/contributors/cli/#build-layout).
