These workflows run only on the GAIA repo; `.gaia/release-exclude` keeps them out of the release bundle. Each workflow's `name:` starts with `GAIA: `, and a CLI test checks that it does. The workflows that ship to every project (Tests, Chromatic, PR Conventions) are documented in [Git hooks and conventions](/workflow/git-conventions/#github-workflows-that-ship).

None of these workflows runs the pre-merge audit. The audit runs locally, through the [Code Audit Team](/workflow/code-audit-team/).

## release.yml

Triggers on `v*.*.*` tag pushes. Builds and publishes the release bundle.

1. **Checkout** at the tag with full history, and derive the version.
2. **Verify `.gaia/VERSION` matches the tag**, so a stray tag cannot publish.
3. **Extract the CHANGELOG section** for the release; fails when the heading is missing.
4. **Verify the manifest is up to date** and **the wiki was scrubbed** for release.
5. **Verify the committed CLI bundles** match a fresh build from `.gaia/cli/src`.
6. **Stage the release tree** from `git ls-files`, minus `.gaia/release-exclude`.
7. **Bundle-time scrub**: removes `gaia:maintainer-only` blocks and checks that no contributor-only content leaked into the shipped files.
8. **Verify runtime dependencies** against the staged tree.
9. **Distribution test gate**: `bash .gaia/tests/distribution/run-all.sh` (Layers 0 and 1). A failure stops the release before anything publishes.
10. **Build** `gaia-bundle-<tag>.tar.gz` and its `.sha256`. The `gaia-bundle-` prefix is deliberate. A 1.6.1 `/update-gaia` looks for `gaia-<tag>.tar.gz`, so the new name makes it fail at the download instead of misreading the new folder layout.
11. **Compose the release body**, starting with the line that sends 1.6.1 projects to the 2.0.0 migration, then **create the GitHub Release** with both files.

## cli-tests.yml

Its jobs run on pull requests to `main` and on `workflow_dispatch`. The workflow also lists pushes to `main` as a trigger, but every job skips on a push. The `workflow_dispatch` run is how you produce the required check on a commit that got no pull-request run. Three jobs:

- **Vitest (`.gaia/cli`)** (required): for the CLI, typecheck, lint, and the Vitest tests. It also runs the bats tests for region markers, checks that the committed CLI bundles match a fresh build from source, runs the fitness lint over GAIA's own harness, and checks that the third-party skills copied into the repo (vendored skills) match the hashes recorded under `.gaia/vendor`. On a pull request, most steps run only when the change touches the files they cover; a `workflow_dispatch` run runs every step.
- **Distribution harness** (advisory): the distribution tests that need neither Docker nor a token.
- **Shipped-surface leak check** (advisory): builds the release tree, then checks that no shipped file names a contributor-only path and that removing the maintainer-only blocks leaves no partial marker behind.

## audit-ci-tests.yml

Like `cli-tests.yml`, its jobs run on pull requests to `main` and on `workflow_dispatch`, and skip on a push to `main`. Runs GAIA's bats tests for the shipped scripts and hooks (`.gaia/scripts/tests/`, `.github/audit/tests/`, `.gaia/tests/`), split across parallel jobs (shards). It also runs the [commitlint](https://commitlint.js.org/) tests and the tests for the RED gate (the check that a test was seen failing first) that need Node or Chromium. A final `Audit CI Tests` job passes only when every shard passes, so one required check covers them all.

Projects get these scripts as code GAIA controls and never edit, so the tests only need to catch changes made on the GAIA repo.

## shell-lint.yml

Triggers on pull requests to `main`. Two advisory jobs:

- **Shellcheck**: runs shellcheck over every tracked `*.sh` and `*.bats` file through `.gaia/tests/shell-lint.sh`.
- **Bash 3.2 parse**: on a macOS runner, checks that every tracked `*.sh` file parses under the `/bin/bash` 3.2 that ships with macOS, since GAIA's shell scripts must run there.

## forensics-triage.yml

Triggers on issues `opened` or `labeled` with `gaia-forensics`, the label [`/gaia-forensics`](/maintenance/forensics/) files with. Runs Claude Code to triage the report. It skips an issue already labeled `gaia-triaged`, then parses the report, classifies it, and checks whether the fix is in scope. For an in-scope fix it creates a fix branch, runs the Quality Gate, and opens a draft pull request. A final step always adds the `gaia-triaged` label, however the run went.

Its helpers live in `.github/forensics/`, all contributor-only. The scope check rejects any edit under `.github/workflows/`, so triage can never change its own workflow; that is a security boundary.
