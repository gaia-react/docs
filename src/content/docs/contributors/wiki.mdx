Two directories under `gaia/wiki/` are excluded from the release bundle by `.gaia/release-exclude`:

- `wiki/entities/`: named systems, products, and people tracked across the codebase.
- `wiki/meta/`: process and convention pages about the wiki itself.

Individual concept and decision pages are excluded too, each because its subject is maintainer-only: `wiki/concepts/Release Workflow.md`, `wiki/concepts/Release-Notes.md`, `wiki/decisions/Bundle-time Scrub.md`, `wiki/decisions/CLI-Binary-Split.md`, `wiki/decisions/Folding Shell Scripts into the CLI Binary.md`, `wiki/decisions/Forensics Triage Workflow.md`, `wiki/decisions/Sharded CI Test Matrix.md`, `wiki/decisions/Shell Guard Fixture Discrimination.md`, `wiki/decisions/Local Test Runtime.md`, and `wiki/decisions/Dependabot as a Data Source.md`. `.gaia/release-exclude` is the authoritative list.

The wiki workflow every project runs, [`/gaia-wiki`](/maintenance/wiki/), is in the main docs. This page covers content contributors maintain on the GAIA repo's own wiki.

## wiki/entities/

Pages here describe named entities the GAIA team tracks. Current entries:

- `GAIA.md`: the project itself, including history, naming convention, and supporting links.
- `Steven Sacks.md`: author and maintainer.

Entity pages use the `entity` type in their frontmatter, with an `entity_type` field saying what kind of entity it is (`project`, `person`, etc.).

When to add: give an entity its own page once concept or decision pages link to it and a page of its own helps tell it apart from similar names. Generic concepts go under `wiki/concepts/`, not here.

## wiki/meta/

Pages here describe the wiki's own process. `/gaia-wiki` writes two reports here, each overwritten on every run, with earlier runs in the commit history:

- `wiki/meta/lint-report.md`, from the lint stage.
- `wiki/meta/consolidate-report.md`, from the consolidate stage.

Do not write these by hand. The directory is release-excluded, so a fresh project has no `wiki/meta/` until its first `/gaia-wiki` run creates it.

When to add: a new meta page is appropriate when it documents how the wiki itself works (a new convention, a new dashboard, a new workflow).

## wiki/.state.json

`wiki/sync` and `wiki/consolidate` share a single state file at `wiki/.state.json`. Only CLI subcommands write it, and each write replaces the file in one step. Do not edit it by hand while a workflow is running.

| Field | Written by | Value |
|---|---|---|
| `version` | `state-init` | Always `1`. |
| `last_evaluated_sha` | sync | Full 40-char SHA of HEAD at the last sync evaluation. |
| `last_evaluated_at` | sync | ISO-8601 timestamp of the last sync evaluation. |
| `last_consolidated_sha` | sync (bootstrap) / consolidate | Full 40-char SHA at consolidate completion; bootstrapped by sync on first run. |
| `last_consolidated_at` | consolidate | ISO-8601 timestamp at consolidate completion. |

`gaia wiki state-init <sha>` creates the file on a fresh project (refuses if it already exists). `gaia wiki state-bump <field> <value>` updates a single field and preserves all others. `gaia wiki state --json` reads the file and reports how far the wiki has fallen behind the code (drift severity), the head SHA, and page counts per domain.

## gaia wiki CLI primitives

`gaia wiki` has these subcommands. `/gaia-wiki` and its subagents call them; you rarely run them by hand except to debug.

| Subcommand | Description |
|---|---|
| `state [--json]` | Drift report: commits since `last_evaluated_sha`, severity, page counts per domain. |
| `commit-classify --since <sha> [--json]` | Mark each commit since `<sha>` as `WORTHY` (worth a wiki update) or `SKIP`. |
| `state-init <sha>` | Create `wiki/.state.json` (refuses if the file already exists). |
| `state-bump <field> <value>` | Update one field in `wiki/.state.json`, keeping all the others. |
| `log-prepend --sha <h> --decision <D> --reason "..."` | Prepend a decision line to `wiki/log.md`. |
| `page-index [--json]` | List every wiki page with its frontmatter and wikilinks. |
| `orphans [--json]` | Pages no other page links to. |
| `near-collisions [--max-distance N]` | Page names in the same domain that differ by only a few characters (Levenshtein distance). |
| `dead-paths [--json]` | Repo paths written in backticks in wiki text that no longer exist. |
| `frontmatter [--json]` | Pages missing required frontmatter (`type`, `status`). Excludes `wiki/meta/`. |
| `empty-sections [--json]` | Headings with no content and no subheadings; a heading with subheadings is never flagged. |
| `broken-links [--json]` | Wikilinks whose target page does not exist. |
| `chain <begin\|commit\|finish\|refresh-nudge>` | Runs the full `/gaia-wiki` chain on one branch with one pull request. |

`chain` subcommands:

- `begin` runs on the branch `/gaia-wiki` already created (a `wiki/<YYYY-MM-DD-HHMM>` branch, in a worktree by default) and refuses `main` and `master`.
- `commit` commits every stage's `wiki/` edits as one commit titled `wiki: <date> <time> UTC`; a no-op when nothing changed; refuses when non-wiki changes are present.
- `finish` pushes the branch, opens one pull request, posts a `GAIA-Audit` status marking the change as outside the audit's scope, and queues auto-merge. It deletes the branch if nothing changed.
- `refresh-nudge` updates the statusline's wiki nudge after the merge, from the main checkout's new drift.

## gaia:maintainer-only block convention

Some files that ship contain blocks that do not: pages under `wiki/concepts/` and `wiki/decisions/`, files under `.claude/` such as `.claude/rules/pr-merge.md`, the `.gaia/audit-ci.yml` roster, and `.githooks/pre-commit`. The block convention is:

```markdown
<!-- gaia:maintainer-only:start -->
This block is contributor-only. It gets stripped from the release
tarball by the bundle-time scrub during release.
<!-- gaia:maintainer-only:end -->
```

The shipped file is a subset of the source: the scrub removes the markers and everything between them before the tarball is built. The literal phrase is `maintainer-only`; this is the on-disk identifier and matches the comment text in `.gaia/release-exclude` and the step name in `release.yml`. Public-facing references in the docs site use "Contributors."

When to use the block convention rather than path-level exclusion: use blocks when most of a page is relevant to every project but a section needs to stay internal. Use path-level exclusion (an entry in `.gaia/release-exclude`) when the entire file is contributor-only.
