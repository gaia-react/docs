`/setup-gaia` is the single onboarding command for a GAIA project. Run it once after `/gaia-init`, and re-run it any time. It detects the situation and runs only the phases this clone actually owes:

- **Per-machine work** every clone needs: tool installs, plugins, the spec-kit runtime, the statusline bit, `.env`, and the optional adaptation feature.
- **GitHub repository provisioning**: create, adopt, or set one up manually. Private by default.
- **CI wiring** when a repo exists and you are a repo admin.
- **Your per-developer audit-mode choice**: CI or local at merge time.

It is safe for **any developer** to run at **any time**.

## When to use this

- After `/gaia-init` on a project you created with `npx create-gaia`.
- After `git clone`-ing an existing GAIA project, once per machine.
- Any time you want to add GitHub or CI to a project that skipped it earlier.

GAIA's statusline prompts `Run /setup-gaia` until the per-machine setup is finished.

A plain (no-flag) re-run on a fully provisioned project prints the already-configured line and changes nothing. It never re-provisions the repo, rotates the token, or touches branch protection. Pass `--reconfigure` to rotate the bot token and re-select which tools run on cron.

## What runs, and when

The command classifies your clone (fresh clone, first adopter, partial re-run, provisioned, or an admin teammate on an unwired clone) and routes only the owed phases. Each phase re-checks its own completion and no-ops when already done, so a re-run is always safe and misclassification cannot corrupt state.

### Prerequisites (every run)

Three checks run on every invocation and never block setup:

- **Worktree self-heal.** If you set up the clone from a git worktree created outside Claude Code, the shared-state symlinks are recreated. In a normal checkout this is a no-op.
- **pnpm and node_modules.** If `corepack` is available, pnpm is enabled at the pinned version; otherwise it is installed globally via npm. `pnpm install` runs when `node_modules/` is missing.
- **GitHub CLI check (advisory).** If `gh` is missing or unauthenticated, you get a warning and setup continues. The PR merge gate, `/gaia-plan`, and forensics rely on `gh`, so install it from [cli.github.com](https://cli.github.com/) and run `gh auth login` when you can.

## Phase: per-machine setup

Skipped whole if this clone already finished per-machine setup (a first adopter finishes it inside `/gaia-init`). Otherwise these steps run in order, each recorded so a re-run resumes from the first incomplete one.

### install-tools

Three external tools, identical to step 5 of [`/gaia-init`](/getting-started/gaia-init/#5-claude-tooling):

- **React Doctor** skill. GAIA installs the skill and stays the sole controller of when react-doctor runs: via the skill after edits and the `code-review-audit` agent pre-merge.
- **Playwright CLI** binary, installed globally.
- **Serena** MCP server, with `uv` bootstrapped first if missing. If Serena is already registered, the "name already exists" error is treated as success.

### install-plugins

```bash
claude plugin install typescript-lsp@claude-plugins-official
claude plugin marketplace add AgriciDaniel/claude-obsidian
claude plugin install claude-obsidian@claude-obsidian-marketplace
```

Already-installed plugins are no-ops.

### Automatic steps

Three steps run with no input from you:

- **spec-kit init.** Registers the spec-kit runtime so `/gaia-spec` works in your clone, pinned to the version in the GAIA extension. The repo already ships the GAIA extension and preset; this wires up spec-kit itself.
- **Statusline permissions.** Restores the executable bit on the statusline scripts, which can be lost on cross-platform clones.
- **Environment bootstrap.** If `.env.example` exists and `.env` does not, a copy is made for you.

### Adaptation feature opt-in

You choose whether to opt into an optional adaptation feature. It defaults to off, everything it uses stays on your machine, and you can change the choice later. If the decision was already made (during `/gaia-init`, for example), this step is skipped.

## Phase: GitHub repository

Judged from the actual repo, branch, and push state, not merely whether an `origin` remote exists. If the repo is already provisioned, the command prints `GitHub repository already provisioned.` and moves on. Otherwise, for a first adopter this is the first prompt you see:

- **Create the repo on GitHub** (recommended). Created **private** by default, your default branch pushed, and the recommended defaults applied. Flipping it public or internal requires a separate, explicit confirmation, because a public repo exposes your full pushed history. Secret-scanning push-protection is enabled right after creation where the plan supports it.
- **Adopt an existing repo.** You already have a GitHub `origin`; creation is skipped and the recommended defaults are applied.
- **Set one up manually.** The command prints the `git remote add` / `git push` guidance and leaves GitHub untouched. Re-run `/setup-gaia` once it is pushed.

### Recommended defaults (admin only)

Applied after create or adopt, and only when you are a repo admin with an authenticated `gh`. A non-admin runner skips these with a printed note and setup still finishes:

- **Default-branch protection**, with the `GAIA-Audit` required status check as the merge gate. Approvals are not required and admin enforcement is off on purpose, so a solo adopter can still merge their own PRs.
- **delete_branch_on_merge**, offered when it is off. Enabling it marks GAIA's monthly stale-branches cron as redundant.
- **Dependabot alerts on**, its PR-opening features off. `/update-deps` owns dependency PRs in GAIA; Dependabot is enabled for alert visibility only. If a Dependabot or Renovate config is already present, you are warned about duplicate PRs first (the command never disables either tool for you).

## Phase: CI wiring

Runs when a GitHub repo exists and you are a repo admin. Skipped for non-admins (with a printed note) and short-circuited when CI is already configured and in sync:

```
GAIA CI is already configured. Pass --reconfigure to rotate tokens or change tool selection.
```

If your workflow files have drifted from the current bundled templates (after a GAIA update, for example), the command does not silently exit. It lists the affected workflows and offers to re-render them onto a branch and open a PR you review and merge. You can also skip or run a full `--reconfigure`.

### What GAIA CI installs

Four maintenance workflows on a smart cron. Three open labeled PRs and auto-merge on green CI; the stale-branches job deletes merged branches directly and opens no PR.

| Workflow file | Default schedule | What it does |
|---|---|---|
| `gaia-ci-wiki.yml` | Daily | Runs the `/gaia-wiki` chain (sync, consolidate, lint) and opens one PR |
| `gaia-ci-update-deps.yml` | Weekly | Runs `/update-deps`. Batches minor and patch bumps into one PR; a separate PR per pending major-bump group |
| `gaia-ci-pnpm-audit.yml` | Daily | Runs `pnpm audit`. For each high or critical advisory, opens a security issue and a targeted single-package bump PR |
| `gaia-ci-stale-branches.yml` | Monthly | Deletes branches merged more than 30 days ago. No PR, no auto-merge |

Two cases hold for human review instead of auto-merging, both tagged `needs-human-review`: a wiki PR whose changed lines exceed 25% of the wiki's size at the base commit, and every major-bump PR.

The command also installs `code-review-audit.yml`, the pre-merge audit gate. It is not one of the four cron tools and installs **unconditionally**, even when no cron tool runs in CI. It reads `.gaia/audit-ci.yml` at runtime, and the bot token below authenticates it. See the [`code-review-audit` agent reference](/reference/agents/) for what it checks.

### Team audit-mode policy

Sets the team baseline for how `code-review-audit` runs at merge time, written to `.gaia/audit-ci.yml`:

- **CI audits every PR** (recommended). Every PR's audit runs on CI.
- **Local-first.** Developers who run GAIA locally have the audit run at merge time; CI stands down for them. Each developer still opts in per-person below. Local-first relies on the `GAIA-Audit` required check being registered (this same flow registers it); if that check is ever unconfirmable, the resolver fails closed to CI, so a local stand-down can never leave the branch unguarded.

### Bot token (out of band)

GAIA CI needs an Anthropic token or key to authenticate the workflow steps that call Claude.

Before asking you to set one, `/setup-gaia` checks whether the repo or its organization already exposes a usable secret, matched **by name only, never by value** (`CLAUDE_CODE_OAUTH_TOKEN` takes precedence over `ANTHROPIC_API_KEY`). If one is found, it prints `Detected <NAME> already set at the <repo|org> level; GAIA CI will use it. Skipping token setup.` and skips the rest of this step. You only pick a token type when none is already present:

- **CLAUDE_CODE_OAUTH_TOKEN**, for Claude Code subscribers.
- **ANTHROPIC_API_KEY**, for direct Anthropic API customers.

:::caution[The token value never enters the chat]
`/setup-gaia` never handles your token value. It **prints** a `gh secret set` command for you to run in your **own terminal**, where `gh` prompts for the value with input hidden:

```bash
gh secret set CLAUDE_CODE_OAUTH_TOKEN --repo <owner>/<repo>
```

Do not paste the token into the Claude Code chat. Anything typed into the chat is recorded in the transcript and sent to the model API; piping it to `gh` afterward does not undo that exposure. If you paste it by mistake, treat it as compromised and rotate it. The command verifies the secret by **name only** (`gh secret list`), never its value.
:::

Managing Actions secrets needs repo-admin permission. A non-admin runner gets the instruction to hand off to an admin instead.

### Workflow generation and the required check

The command generates `.github/workflows/gaia-ci-*.yml` from `.gaia/automation.json`, installs `code-review-audit.yml`, and triggers one `workflow_dispatch` run to confirm the first workflow boots. It then registers `GAIA-Audit` as a required status check on the default branch by **unioning** it into the existing contexts, so sibling checks (`Tests`, `Chromatic`) are preserved. Registration needs repo-admin access and a branch-protection rule; if either is missing, the command prints the `gh api` call to run yourself, and the merge gate falls back to CI mode for every author until the check is registered.

If the verification run fails, you can retry, abandon (deletes the generated files, leaves `setup_complete: false`), or commit anyway. On success the command stages the workflow files, `.gaia/automation.json`, and `.gaia/audit-ci.yml`, commits, and pushes.

## Phase: your audit-mode choice

Once the project has CI wired, you choose who runs **your** `code-review-audit` at merge time:

- **CI (default).** CI audits your PRs; you wait for the `GAIA-Audit` check.
- **Locally.** Your audit runs at merge time when you ask Claude to merge, streaming and incremental. CI stands down for you.

Your choice appends a `<login>=<mode>` pair to `audit_authors` in the **committed** `.gaia/audit-ci.yml`, so other developers see it. It lands via a one-line PR that you review, commit, and open yourself; the command prints the exact `git` and `gh` commands and never commits or opens the PR for you. If `gh` is not authenticated when this step runs, it is skipped and will not reappear on a plain re-run.

## Finish

Once every owed step is recorded, per-machine setup is finalized and the command confirms completion. Restart Claude Code so the new plugin and skill state load. After that, the statusline surfaces `/update-deps` and `/update-gaia` indicators when updates are available.

## Reconfiguring

```sh
/setup-gaia --reconfigure
```

`--reconfigure` skips the idempotent short-circuit and re-runs the CI flow: it re-prompts for which tools run on cron, re-offers the audit-mode policy, and asks you to rotate the bot token out of band (running `gh secret set` again overwrites the value silently). If the token is managed at the org level, it is not rotated at repo scope; the command prints `<NAME> is managed at the org level; rotate it there, then re-run. Skipping repo-secret rotation.` `setup_complete` stays `true`; it never re-provisions the repo or changes branch protection.

## On failure: re-run

Every step and CLI primitive is idempotent and safe to re-run on partial state. After fixing the cause (missing auth, a network error, a bad config), just re-run `/setup-gaia`. Each phase detects its own completion and resumes from the first owed step.
