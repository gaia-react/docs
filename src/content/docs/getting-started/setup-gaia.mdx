`/setup-gaia` is the single onboarding command for a GAIA project. Run it once after `/gaia-init`, and re-run it any time. It detects the situation and runs only the phases this clone actually owes:

- **Per-machine work** every clone needs: tool installs, plugins, the statusline bit, `frontend/.env`, the sandbox decision, and, if you have your own global statusline, which statusline draws the left side.
- **GitHub repository provisioning**: create, adopt, or set one up manually. Private by default. When you are a repo admin, it also sets branch protection, registers `GAIA-Audit` as a required check, and offers squash-only merges.
- **Team settings** in `.gaia/project.json`: the git isolation policy and the sandbox recommendation. Both ship with a default, so a plain run records the default and asks nothing.

It is safe for **any developer** to run at **any time**. It is a typed command: Claude never starts it on its own. Run it from the main checkout; inside a linked worktree it refuses and names the main checkout.

## When to use this

- After `/gaia-init` on a project you created with `npx create-gaia`.
- After `git clone`-ing an existing GAIA project, once per machine.
- Any time the statusline shows a `⚙️ /setup-gaia` nudge, or you want to add GitHub to a project that skipped it earlier.

A plain (no-flag) re-run on a fully set up project prints `GitHub repository already provisioned.` and changes nothing. It never re-provisions the repo or changes branch protection. The one exception: a repo admin re-running it on a repo whose required checks still lack `GAIA-Audit` gets the registration.

## What runs, and when

The command classifies your clone (a new project with no GitHub repo yet, a partial re-run, a fresh clone, or a provisioned project) and routes only the owed phases. Each phase re-checks its own completion and no-ops when already done, so a re-run is always safe and misclassification cannot corrupt state.

### Prerequisites (every run)

Three checks run on every invocation and never block setup:

- **Worktree self-heal.** If the clone is a git worktree created outside Claude Code, the shared-state links are recreated (`bash .gaia/scripts/link-worktree.sh`). In a normal checkout this is a no-op.
- **pnpm and node_modules.** If `corepack` is available, pnpm is enabled at the pinned version; otherwise it is installed globally with npm. `pnpm install` runs when `node_modules/` is missing.
- **GitHub CLI check (advisory).** If `gh` is missing or unauthenticated, you get a warning and setup continues. The PR merge gate, `/gaia-plan`, and `/gaia-forensics` rely on `gh`, so install it from [cli.github.com](https://cli.github.com/) and run `gh auth login` when you can.

## Phase: per-machine setup

Skipped if this clone already finished per-machine setup (a new project finishes it inside `/gaia-init`). Otherwise these steps run in order, each recorded so a re-run resumes from the first incomplete one.

### Install Tools

Three external tools, identical to step 5 of [`/gaia-init`](/getting-started/gaia-init/#5-claude-tooling):

- **React Doctor** skill, installed under `frontend/.claude/skills/` by `bash .gaia/scripts/install-react-doctor.sh`.
- **Playwright CLI** binary, installed globally.
- **Serena** MCP server at v1.7.0, with `uv` installed first if missing. If Serena is already registered, the "name already exists" error counts as success.

### Install Plugins

```bash
claude plugin install typescript-lsp@claude-plugins-official
```

Already-installed plugins are no-ops.

### Automatic steps

Two steps run with no input from you:

- **Statusline permissions.** Restores the executable bit on the statusline scripts, which can be lost on cross-platform clones.
- **Environment bootstrap.** If `frontend/.env.example` exists and `frontend/.env` does not, a copy is made for you.

### Sandbox decision

Claude Code's OS-level Bash sandbox is off by default. It sandboxes Bash commands and their child processes, but it breaks `gh`, git over HTTPS, and `docker` until they are allowlisted, and GAIA's lifecycle runs on `gh`.

A plain run asks about it only when your team recommends it (`sandbox_recommended: true` in `.gaia/project.json`). When it asks, it first checks your machine can run it:

- **Native Windows or WSL1**: the sandbox is unavailable. Setup says so, points you at WSL2, and leaves it off.
- **Linux or WSL2 missing bubblewrap or socat**: setup prints the install command and leaves the sandbox off until you install them and re-run.
- **macOS, or Linux with both installed**: one question, with the team's recommendation as the recommended answer. Enabling writes the sandbox settings to `.claude/settings.local.json` (gitignored) and takes effect in your next Claude Code session.

Each machine decides for itself, and your answer is never re-asked on a plain run.

## Phase: GitHub repository

Judged from the actual repo, branch, and push state, not merely whether an `origin` remote exists. On a new project this is the first prompt you see:

- **Create the repo on GitHub** (recommended). If you belong to any GitHub organizations, it first asks where the repo should live, your personal account (the default) or one of your orgs, ranked by your recent commit activity. Created **private** by default, your default branch pushed, and the recommended defaults applied. Making it public or internal takes a separate, explicit confirmation, because a public repo exposes your full pushed history. Secret-scanning push protection is enabled right after creation where GitHub offers it. Creation refuses while the working tree has uncommitted changes, because `gh repo create --push` pushes commits only.
- **Adopt an existing repo.** You already have a GitHub `origin`; creation is skipped and the recommended defaults are applied.
- **Set one up manually.** The command prints the `git remote add` / `git push` guidance and leaves GitHub untouched. Re-run `/setup-gaia` once it is pushed.

### Recommended defaults (admin only)

Applied after create or adopt, and only when you are a repo admin with an authenticated `gh`. A non-admin runner skips these with a printed note, and per-machine setup still finishes:

- **Default-branch protection.** Created only when the branch has no protection rule; an existing rule is kept as it is. Approvals are not required and admin enforcement is off on purpose, so a solo developer can still merge their own pull requests.
- **`GAIA-Audit` as the required check.** GAIA's local merge workflow posts the `GAIA-Audit` status when the [pre-merge audit](/workflow/code-audit-team/) clears. Requiring it is what stops a pull request merged from the github.com button from skipping the audit. The registration adds `GAIA-Audit` to the existing required checks and keeps the others (`Tests`, `Chromatic`, your own). It also drops the 1.x `code-review-audit` context, which nothing posts any more and which would otherwise hold every pull request.
- **`delete_branch_on_merge`**, so GitHub deletes each pull request's branch as it merges, however it was merged. Applied without a question on a repo this run created; asked on an adopted repo.
- **Dependabot posture**: security alerts on, Dependabot's own security-fix pull requests off. [`/update-deps`](/maintenance/update-deps/) reads the alerts and fixes vulnerable packages itself, tested through the quality gate. If a Dependabot npm entry or a Renovate config is already present, you are warned about duplicate pull requests first; the command never edits either file.

If a registration or setting fails (403 without admin, 404 without a protection rule), the command prints the exact `gh api` command to run yourself and continues.

## Phase: team settings

Team settings live in `.gaia/project.json`, which is committed and shared. `/gaia-init` writes GAIA's defaults, so a plain run asks nothing here:

| Setting | Default | What it decides |
|---|---|---|
| `isolation_policy` | `always-worktree` | Whether `/gaia-plan`, `/gaia-debt`, and ad-hoc committed work run in their own git worktree (`always-worktree`), suggest one (`prefer-worktree`), or suggest a branch in your current checkout (`prefer-branch`). See [Work lifecycle](/workflow/work-lifecycle/). |
| `sandbox_recommended` | `false` | What the sandbox question above recommends to each machine. A recommendation only; each machine still decides. |

Only a repo admin running `/setup-gaia --reconfigure` changes them. A new isolation policy is committed and pushed to the default branch straight away, because the team's policy belongs there at once. If a ruleset rejects the push, the command says so and leaves the commit local for you to push or open as a pull request.

## Phase: squash-only merges

GAIA lints pull request titles as Conventional Commits because a squash merge lands the title as the commit subject on the default branch. That holds only when squash is the one merge method and the squash commit takes the PR title.

When you are a repo admin and merges are not already squash-only, setup turns off merge commits and rebase merges and has every squash commit take the PR title as its subject. On a repo this run created it applies without asking; on an adopted repo it asks, since an adopted repo can have a reason to keep merge commits. A Skip is never re-asked on a plain run.

## Phase: labels

`gaia labels sync` creates and renames GAIA's GitHub labels to match its registry and reports color drift without overwriting your colors. See [Labels](/reference/labels/). The step is advisory: a token without label-write scope gets the manual `gh label` commands to run, and setup continues.

## Phase: statusline left side

GAIA's statusline always draws GAIA's nudges on the right. If you have your own global `statusLine.command` in `~/.claude/settings.json`, setup asks which one draws the left side:

- **Use GAIA's statusline bar** (recommended): project, branch, model and effort, and a context bar colored to match the audit checkpoint.
- **Keep my own statusline.**

The answer is per-machine, stored in `.gaia/local/settings.json` (gitignored). On every run, setup also warns when the project's effective statusline does not run GAIA's statusline script, since without it you get no GAIA nudges and the audit loop cannot read your context usage.

## Phase: owed setup features

A later GAIA release can add a setup feature. `/setup-gaia` runs any feature in `.gaia/setup-features.json` that has no recorded decision, so a project whose setup was already complete still picks it up.

## Finish

Project decisions recorded this run (`setup_decisions` in `.gaia/project.json`) are committed and pushed to the default branch as `chore(gaia): record setup decisions`, so they reach your team. Per-machine setup is finalized, the usage ping is sent (see [Usage ping](/getting-started/gaia-init/#usage-ping)), and the command prints one of two closing lines:

- `You're all set: your GAIA project is ready.` when nothing this machine can act on is still owed.
- `Setup isn't finished: these project settings are still owed: ...` naming them, when a GitHub step was refused or skipped. Fix the cause and re-run.

Restart Claude Code so the new plugin and skill state loads.

## Reconfiguring

```sh
/setup-gaia --reconfigure
```

`--reconfigure` re-asks these decisions and nothing else:

- The sandbox decision on this machine. A repo admin's answer also sets the team sandbox recommendation.
- The team git isolation policy (repo admins only).
- The squash-only merge offer (repo admins only).
- The statusline left side.

It never re-provisions the repo or changes branch protection.

## On failure: re-run

Every step is idempotent and safe to re-run on partial state. After fixing the cause (missing auth, a network error, a bad config), re-run `/setup-gaia`. Each phase detects its own completion and resumes from the first owed step.
