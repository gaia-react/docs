Hooks are scripts Claude Code runs at set moments: before or after a tool call, when a session starts or stops, and when you send a message. GAIA registers them in `.claude/settings.json`. The app's `frontend/.claude/settings.json` is generated from the root settings plus an overlay file, so the same hooks run in both places. The scripts live in `.claude/hooks/`.

Unlike [rules](/reference/rules/), which Claude reads and follows, hooks are scripts that always behave the same way. A guard hook blocks a tool call no matter what the model decided, and its message tells you the allowed form of the command or the next step. A permission mode that skips prompts, such as auto mode, does not skip hooks.

Some advisory hooks that react to `git` or `gh` commands carry an `if` filter, so they start only for the commands they apply to. Guard hooks never have one, so they always run. Each hook command finds its script from the root of the checkout the shell is in (`git rev-parse --show-toplevel`). A `cd` within the same checkout changes nothing. A `cd` into another checkout makes the hooks look for their scripts there instead: a clone without them runs no guards at all, and nothing reports it. That is why the `shell-cwd` rule bans `cd`. When `jq` is missing, a blocking hook refuses the call rather than letting it through.

Why each guard exists, and how to clear it, is in the [gate reference](/reference/gates/).

## Guards (can deny a tool call)

### Bash and Monitor commands

| Hook | Denies |
|---|---|
| `block-main-destructive-git` | Commits on `main` or `master`, force-pushes that name them, any push from them or that pushes `main`, `master`, or `HEAD`, and a `git checkout` or `git switch` that would move the main checkout off another session's open-PR branch. |
| `block-no-verify` | `git commit` or `git push` with `--no-verify`, `-n` on a commit, or `-c core.hooksPath=<path>`. |
| `block-rm-rf` | `rm -rf` of `/`, an absolute path outside the allowed scratch folders, `$HOME`, `.`, `*`, dotfile globs, `.git`, `.claude` and its children, and `node_modules`, plus `--no-preserve-root`. Scratch paths and the session scratchpad are allowed. |
| `block-sensitive-read` | Reading dotenv files (`.env` and every `.env.<name>` except `.env.example`), keys (`.key`, `.pem`), credential files, and anything under a `secrets` directory, through any Bash command that reads files, `source`, redirects, and filter flags such as `rg -g '*.key'`. Also plain `env` or `printenv`, which print every environment variable. Also registered on Read and Grep. |
| `block-manifest-write` | Writes to `.gaia/manifest.json`, which lists only the files GAIA ships. `/update-gaia` writes it through a specific exemption. |
| `block-invalid-pr-title` | A `gh pr create` or `gh pr edit` whose title would fail the PR Conventions lint once it becomes the squash-merge commit message (the title plus ` (#<n>)`), and `--fill` with no `--title`. |
| `block-pr-create-without-draft` | A `gh pr create` for this repository without `--draft`. |
| `block-fork-pr-checkout` | `gh pr checkout` or a `git fetch` of `pull/<n>/head` for a pull request from a fork, or one that `gh` cannot identify as fork or not. |
| `block-handrolled-pr-poll` | A shell loop that checks `gh pr view` or `gh pr checks` over and over without reading `mergeable`; use `bash .gaia/scripts/pr-wait-merge.sh --pr <N>`. |
| `pr-merge-audit-check` | `gh pr merge` until every Code Audit Team member responsible for the changed files has approved it. For a pull request outside the audit's scope, or a `chore(deps)` pull request that only changes dependency manifests, it posts the `skipped:` status itself. |
| `worthiness-presence-check` | `gh pr merge` when a changed test has no worthiness record for its current content. In scope: stories, [Playwright](https://playwright.dev/) tests, and component or page tests whose result the classifier finds is not predictable. It checks only that the record exists, not its verdict. |
| `red-verify-commit-check` | `git commit` of a new, passing test for code with predictable output (utilities, parsers, hooks) that was never seen failing. Exemptions are listed under [the RED gate](/reference/gates/#test-seen-failing-first-red-gate). |
| `block-audit-loop-write` | Writes to the audit loop's protected state and context readings, and running by hand the scripts that record a person's grant. |

### Edit, Write, and MultiEdit

| Hook | Denies or asks |
|---|---|
| `block-secrets-write` | Content that contains an AWS key, a GitHub token, a private key header, or a variable with a secret-sounding name set to a real-looking value (including `export`, `declare`, and `local` forms), and any write to a `.env` file except `.env.example`. |
| `block-eslint-config-edit` | **Asks** you to confirm any edit to an `eslint.config.*` file, and explains why: a config edit can silence a rule just as easily as it can make an approved migration. |
| `block-manifest-write` | Writes to `.gaia/manifest.json`. |
| `block-worktree-path-mismatch` | An edit whose path points into a different checkout than the worktree the session is working in. Writes to the main checkout's `.notebook/` are exempt. |
| `block-audit-loop-write` | Writes to the audit loop's protected state. |

### Agent and Task dispatches

| Hook | Limits |
|---|---|
| `audit-loop-bound` | Each start of the audit loop or of a Code Audit Team member, per branch. It checks the context checkpoint, whether rounds are still making progress, and the hard limit on rounds, and blocks at a checkpoint until a person answers. |

## Recorders and context

These hooks never block anything. They record what happened (test failures, grants, usage) or add guidance to the session at the right moment.

| Hook | Event | What it does |
|---|---|---|
| `audit-loop-grant` | UserPromptSubmit | Records `audit-grant <n>` or `audit-accept`, typed as your whole message in an interactive session. |
| `audit-loop-ask-grant` | PostToolUse (AskUserQuestion) | Records your answer to the audit checkpoint's question. |
| `post-findings-block-on-merge` | PreToolUse (`gh pr merge`) | Posts one comment collecting the pull request's audit findings, which `/gaia-codify` later counts. Never blocks. |
| `capture-red-observations` | PostToolUse and PostToolUseFailure (Bash) | Records failing test runs, so the RED gate can see a test failed before it passed. |
| `capture-gh-artifact` | PostToolUse (`gh pr create`) | Links the pull request to its branch in the usage ledger. |
| `pr-merge-cost` | PostToolUse (`gh pr merge`) | Prints the pull request's cost box. |
| `issue-claim-release` | PostToolUse (`gh pr merge`) | Removes `in-progress` from every issue the merged pull request closes, once the merge is confirmed. |
| `debt-sentinel-touch` | PostToolUse (`gh` issue and merge commands) | Refreshes the statusline's tech-debt count. |
| `workflow-doctrine-inject` | SessionStart, PostToolUse (EnterWorktree, `git`, `gh pr checkout`) | Adds GAIA's working rules to the session when it works on a branch or in a worktree, and redirects a plain `git worktree add` under `.claude/worktrees/` to `EnterWorktree`. |
| `context-checkpoint-inject` | PostToolUse | When context use reaches the red, fire, or skull level on the statusline, tells the main session to save its place and ask whether to continue or clear. |
| `context-checkpoint-subagent` | PostToolUse | The same checkpoint for a sub-agent that was given a file to save its place in. |
| `provision-worktree` | SessionStart, PostToolUse (EnterWorktree) | Links shared files into a worktree, gives it its own set of ports and a port file, and installs dependencies and typed routes. |
| `ports-session-start` | SessionStart | Records which session started which dev server, and stops servers left behind by ended sessions and removed worktrees. |
| `wiki-session-start` | SessionStart | Cleans up after a `/gaia-wiki` run whose session ended before its merge finished (deletes the leftover local wiki branch and updates the base branch), and lists merged worktrees with the commands to remove them. |
| `debt-session-reconcile` | SessionStart | Re-checks the `/gaia-debt` count shown on the statusline against GitHub. |
| `usage-capture` | SessionStart, Stop | Records the session's model usage to the local usage ledger. |

`local-janitor.sh` and `post-audit-status.sh` ship in `.claude/hooks/` but are not registered as hooks themselves. The session-start hook runs the first, and the merge workflow calls the second to post `GAIA-Audit`.

## Not hooks, but enforced

- **Native git hooks** in `.githooks/`: `pre-commit` (typecheck, [lint-staged](https://github.com/lint-staged/lint-staged), tests) and `commit-msg` ([commitlint](https://commitlint.js.org/)). See [Git hooks and conventions](/workflow/git-conventions/).
- **Permission rules** in `.claude/settings.json`: for example, Claude cannot edit `pnpm-lock.yaml` directly; `pnpm install` regenerates it.
- **The `GAIA-Audit` required check** on GitHub, registered by [`/setup-gaia`](/getting-started/setup-gaia/).

## Your own hooks

If you register hooks of your own in `.claude/settings.json`, check that each command finds its script wherever the shell happens to be. Copy the form from a registration already in the file:

```bash
bash .gaia/scripts/check-hook-command-rooting.sh .
```

The check reads only `.claude/settings.json`. Hooks in `.claude/settings.local.json` are not checked.
